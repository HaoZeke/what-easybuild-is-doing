* What EasyBuild is built to be good at
EasyBuild builds software from source reproducibly into a curated generation of exact versions.
EasyBuild produces modulefiles for a shared system whose users outnumber its maintainers by three or four orders of magnitude.
Exact pins, generation timing, and from‑source build costs are covered respectively in [[file:03-a-pin-is-for-one-generation.org][A pin is for one generation]], [[file:08-one-easyconfig-many-installs.org][One easyconfig, many installs]], and [[file:10-build-your-own-without-asking.org][Build your own, without asking anyone]].
A generation means the whole stack moves at once typically once a year.
From‑source builds take hours translating into a few hundred extensions and user‑defined problems.
Modulefiles make the artifact an environment rather than a copyable directory.
These trade‑offs suit a national supercomputer serving thousands of users.
They are unsuitable in many other contexts.
The remainder of this chapter addresses the drawbacks.
* When the answer is a different tool for the same job
Three scenarios provide a genuine alternative rather than a complaint.
** A Python environment that changes weekly
Eleven PyPI packages are required.
Twelve additional packages are needed the following week.
A different version of one package is required the week after.
Using EasyBuild requires an easyconfig for each change.
EasyBuild requires a build for each easyconfig.
EasyBuild requires a module for each result.
The stack generation is pinned to annual changes.
Requirements change weekly.
Alignment is prevented.
The appropriate solution is a Python module provided by EasyBuild combined with a virtual environment owned by the researcher.
Invoking =pip= within a venv after =module load Python= supplies the weekly cadence.
Invoking =uv= within a venv after =module load Python= supplies the weekly cadence.
It retains control of the interpreter within the stack.
It retains control of the compiler within the stack.
It retains control of the numerical libraries within the stack.
Components needing reproducibility receive reproducibility.
Components needing speed receive performance.
The failure mode of handling everything within EasyBuild is not lack of functionality.
A maintainer becomes the bottleneck for another's research week.

* When another packaging system fits the problem better
Two systems address a similar problem with different trade‑offs.
The comparison should be stated precisely.

*Spack* expresses dependency constraints as ranges and resolves them for each installation ([[cite:gamblinSpackPackageManager2015][Gamblin et al. 2015]]).
The expression =depends_on('hdf5@1.10:')= is a real lower bound.
A concretiser selects a version that satisfies all such bounds, with variants chosen at install time.
That approach contrasts with the trade described in A pin is for one generation.
Spack's format can retain the constraint that the software actually possesses.
A package to move across environments without modification.
Two installations on the same machine may legitimately differ.
Reproducing a result requires recording the resolved graph instead of naming a generation.

*conda-forge* distributes binaries and performs solving over a channel.
Installation is a download and a solve rather than a build.
This yields a working environment in minutes, identical on a laptop and on a cluster.
In return, those binaries are built for portability rather than for a specific machine's instruction set.
Exploiting a specific instruction set is the purpose of an HPC stack.
Thus the question is not which system is best.
It concerns which cost is acceptable.

- EasyBuild provides exact versions, one stack per generation, tuned builds, hours per package, one generation per year, and a maintainer in the loop.  
- Spack offers real version ranges, per‑install resolution, tuned builds, hours per package, and a resolved graph that must be captured to reproduce.  
- conda-forge delivers minutes per environment, identical results on a laptop and a cluster, and binaries built for portability rather than for the instruction set already paid for.  

A site operating a large machine typically employs more than one of these systems for different user populations.
This is a sound arrangement rather than an admission of defeat.

* The end of the book
EasyBuild's design provides exact versions, curated generations, from-source builds and modulefiles for a shared machine with many more users than maintainers.
Each of those elements is a trade.
A requirement that changes weekly does not belong in an annual generation.
Software without source is a runtime to wrap rather than a build to fake.
A stack needed only to *have* already exists.
What survives all of that is a habit of asking what a thing actually says.
An easyconfig says less than it appears to.
A toolchain is not a label but the top of a computed hierarchy.
A toolchain decides what your dependencies are allowed to see.
A version beside a dependency is an exact pin for one generation and not a minimum.
A filename is a query.
The answer depends on three lists set in three different places.
A checksum concerns bytes and nothing else.
A green build describes one tree on one machine.
None of those are EasyBuild questions.
EasyBuild is a good place to learn them.
There is no default EasyBlock.
There are no version ranges.
There is no guessing.
A tool that does not guess shows where the uncertainty actually is.
Take that.
The rest is documentation.
