#+TITLE: One easyconfig, many installs
#+OPTIONS: toc:nil num:nil

#+begin_objectives
1. Say what =exts_list= installs, and which earlier chapters then apply
 per entry.
2. Say what =%(name)s= means inside an extension's options, and what it
 does not.
3. Read a failure inside a bundle back to the entry that caused it.
#+end_objectives
Every easyconfig up to now installs one component.
The following template installs hundreds of components.
It forms the majority of a real software stack.
#+begin_src easyconfig :widget parse
easyblock = 'Bundle'

name = 'ExampleRSet'
version = '1.0'
versionsuffix = '-R-%(rver)s'

toolchain = {'name': 'foss', 'version': '2025a'}

dependencies = [
 ('R', '4.4.2'),
]

exts_defaultclass = 'RPackage'
exts_filter = ("R -q --no-save", "library(%(ext_name)s)")

exts_default_options = {
 'source_urls': ['https://cran.r-project.org/src/contrib/'],
 'source_tmpl': '%(name)s_%(version)s.tar.gz',
}

exts_list = [
 ('directlabels', '2024.1.21', {
 'checksums': ['9b2e780410bc7812fe155afba9181653293ca657b0b10e1618242dad4d619775'],
 }),
 ('latex2exp', '0.9.6', {
 'checksums': ['fc03bfa663231b60e1edace7b3001a7eb395b4ca468c6a983673845ddd63cb8a'],
 }),
]
#+end_src
Two extensions are present here.
A genuine one of them contains two hundred.
Each entry involves its own download, its own build, and its own check.
The final module consists of a single module.
* The [[file:01-an-easyconfig-is-python.org][An easyconfig is Python]] rule inverts here
=easyblock = 'Bundle'= An easyconfig is Python states that a missing =easyblock= line claims a software-specific easyblock exists.
Naming a generic one is the only way to obtain it.
This easyconfig names one.
Then look at =exts_defaultclass=.
That is the easyblock for the extensions.
It is a default.
An entry in =exts_list= can override it with its own =easyblock= key.
An easyconfig is Python also states that EasyBuild does not guess.
The two parameters which could soften that rule both default to true.
There was one exception, named and then set aside:
#+begin_quote
The one caller that does pass false is the *extensions* machinery,
where falling through to a generic extension handler is the right
behaviour.
#+end_quote
The extensions machinery acts as the caller.
Extensions receive a default.
The strictness described in An easyconfig is Python arises.
* Templates rebind inside an entry

Look at =source_tmpl= in =exts_default_options=:

#+begin_example
'source_tmpl': '%(name)s_%(version)s.tar.gz'
#+end_example
=%(name)s= is not =ExampleRSet=.
=%(version)s= is not =1.0=.
Within an extension, those templates resolve to that extension's own name and version.
The line becomes =directlabels_2024.1.21.tar.gz= for the first entry.
The line becomes =latex2exp_0.9.6.tar.gz= for the second.
That rebinding makes =exts_default_options= useful.
A single =source_urls= and a single =source_tmpl= apply to two hundred extensions without repetition.
Both scopes share the same spelling, causing confusion.
=%(version)s= inside an extension option does not reach the *bundle's* version.
=%(ext_name)s= in =exts_filter= is a distinct third element, intentionally spelled differently.
This occurs.
#+ATTR_EB: :id EB-Extensions-1 :title Which name is this
#+begin_exercise
A bundle is named =ExampleRSet=, version =1.0=, and its
=exts_default_options= carries:

: 'source_tmpl': '%(name)s_%(version)s.tar.gz',

Its =exts_list= has an entry for =latex2exp= at =0.9.6=.

1. What filename does that entry download?
2. A colleague asks for the bundle's own version in an extension's option
 and writes =%(version)s= there. What do they get?
3. They then try =%(ext_version)s= for the extension's version in the
 bundle's own =versionsuffix=. Why is that a different kind of
 question?

#+begin_solution
=latex2exp_0.9.6.tar.gz=. Inside an entry, those templates bind to the
extension, which is exactly what lets one =source_tmpl= serve two
hundred rows.

They get =0.9.6=, the extension's version, not =1.0=. The rebinding is
not optional and there is no template inside an entry that reaches back
out to the bundle. If they need =1.0= there, they have to write it.

The third is different
one of its extensions, and the bundle is evaluated before any of them.
=%(ext_name)s= exists for =exts_filter=, which is a template the bundle
expands once per extension at check time; a =versionsuffix= is resolved
long before that and has no extension in scope to ask about.
#+end_solution
#+end_exercise

* Chapters 6 and 7 now apply once per extension
The =exts_filter= function is the sanity check for each extension referenced in [[file:06-what-installed-means.org][What "installed" means]].
It possesses an unusual shape.
#+begin_example
("R -q --no-save", "library(%(ext_name)s)")
#+end_example
A pair is composed of a command and the standard input supplied to it.
The check for =directlabels= invokes R and requests it to load the library.
The Python equivalent is =("python -c 'import %(ext_name)s'", '')=, with an empty second element.
This represents the strong kind of check described in What "installed" means, executed rather than existence‑tested, and a bundle obtains it for every extension at once.
Two hundred extensions cause two hundred loads, each delivering a real verification.
Every entry includes its own =checksums=, which is [[file:07-a-checksum-is-a-claim-about-bytes.org][A checksum is a claim about bytes]] two hundred times over.
Each extension possesses its own bytes, its own source URL, and its own chance for a checksum that is right about the wrong artifact.
* What that costs, and why it matters when reading a failure
Each bundle contains one module and hundreds of builds.
The implications are practical.
Two hundred serial downloads and two hundred serial compiles require hours.
The mental model is "running two hundred small builds in one process" rather than "installing R packages".
Failures can occur in the middle.
If extension 140 of 200 fails, the requested package continues.
One extension fails and the error identifies that extension.
Reading that failure follows the unchanged discipline of an easyconfig in Python.
The error states the consequence and the question is which entry produced it and what that entry declared.
The entry is identified by a line in =exts_list= and any =exts_default_options= key it inherited implicitly.
The inheritance is the aspect to monitor.
An entry that fails may declare almost nothing, taking its source URL, its template, and its easyblock from three different defaults above it.
Those defaults do not appear in the failure.
* What scales, and what does not
=exts_list= allows one easyconfig to install several packages.
The previous three chapters apply per entry instead of per file.
Each extension specifies its own sources, checksums, easyblock, and runs a check using =exts_filter=.
Two aspects fail to scale.
The rule that an easyconfig is Python's is inverted.
Templates are rebound: =%(name)s= within an entry expands to the extension's name.
This permits a single =source_tmpl= to produce two hundred rows and makes attempts to retrieve the bundle's own version fail.
When a bundle fails, the failure appears in a single entry.
Inspect that entry along with the defaults defined above it.
The next chapter discusses hooks, the supported way to modify EasyBuild behavior without editing an easyconfig.
