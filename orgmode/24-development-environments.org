#+begin_objectives
1. Find the four artifacts EasyBuild already left inside every
 installation, and say what each one reproduces.
2. Load a build's own environment from its devel module, and say what
 that module contains beyond the environment.
3. Choose between a devel module, a dumped script, a =BuildEnv= module
 and a container, on stated grounds.
#+end_objectives
[[file:14-the-isolation-policy.org][The isolation policy]] measured that loading =foss/2025a= sets =EBROOTFOSS=; =$CC= remains unset.
EasyBuild constructs the build environment during =prepare=.
That environment is gone when the build exits.
The rest of this page says where a copy of it remains.
* Look inside the installation first
Each successful installation includes a rarely opened subdirectory.
#+begin_src ebtranscript :source "EasyBuild 5.3.1 from PyPI, local workstation, 2026-09-10; a Tarball install of a one-file test package" :caption "What ends up in <installdir>/easybuild/"
$ find ebtest/software/wobble/1.0 -type f | sed 's#.*/1.0/#1.0/#'
1.0/wobble
1.0/easybuild/easybuild-wobble-1.0-20260910.072006_test_report.md
1.0/easybuild/wobble-1.0.eb
1.0/easybuild/easybuild-wobble-1.0-20260910.072006.log
1.0/easybuild/wobble-1.0-easybuild-devel
1.0/easybuild/reprod/wobble-1.0.env
1.0/easybuild/reprod/wobble-1.0.eb
1.0/easybuild/reprod/easyblocks/tarball.py
#+end_src
One binary and seven files describe how it was built.
Take them in the order they become useful.
=wobble-1.0.eb= is the easyconfig used, archived beside the software.
The recipe for any installed item resides on the machine regardless of the repository status.
=easybuild-...log= is the full build log, kept for reference.
The log is linked from [[file:20-reading-a-failed-build.org][Reading a failed build]].
=..._test_report.md= is a test report, written whether or not one was requested.
The report confirms the claim in [[file:23-testing.org][Testing, and the four things it can mean]] on disk.
=reprod/= is the key directory.
It contains separate answers to the question how to repeat the build.
=reprod/wobble-1.0.eb= is the easyconfig dumped from the parsed configuration.
=reprod/wobble-1.0.env= is a shell script that recreates the build environment.
=reprod/easyblocks/tarball.py= is the source of the easyblock that ran.
No other file provides that source.
An easyconfig plus a toolchain does not fully determine a build.
Archiving the set makes the installation a self‑describing artifact.
It contains the recipe.
It contains the environment.
It contains the program that interpreted them.
The framework performs this before steps run, in =main.py=.
=reproduce_build= creates the directory.
=dump_env_easyblock= writes the environment script into the directory.
=copy_easyblocks_for_reprod= adds the easyblocks.
It adds easyblocks used by bundle components and extensions.
#+ATTR_EB: :id reprod-dir :title What reprod/ contains, and what is missing from it :kind reference
#+begin_detail
| File | Reproduces |
|---+---|
| =<ec>.eb= | the recipe, as parsed |
| =<ec>.env= | the module loads and the toolchain's environment variables |
| =easyblocks/*.py= | the easyblock source, plus component and extension easyblocks |

What is *not* in there, and matters when the file is used a year later:

- the EasyBuild framework version, which is in the log rather than here;
- the source archives, which are in =sourcepath= or upstream;
- the dependency *installations*, which are modules elsewhere in the
 tree; the =.env= names them, and if they were removed it names things
 that no longer exist;
- the operating system and its libraries, which is what
 [[file:11-eessi-somebody-elses-stack.org][EESSI, somebody else's stack]]'s
 compatibility layer exists to pin.

=--minimal-build-env= and =--skip-sanity-check= change what gets
written: a run with =--sanity-check-only= deliberately skips "build
stats, easyconfigs archive, reprod files", so an installation checked
that way carries less than one built normally.
#+end_detail

* The devel module

#+ATTR_EB: :title What is in it
#+begin_predict
Every install carries a devel module whose purpose is to reproduce the
build's environment. Before reading the next block: name three variables
expected in it, and one that would be a problem to find.

#+begin_reveal
=$CC=, =$CXX= and the toolchain's flags are there, which is the point.

The one to be unhappy about is =$PATH=, and it is there in full. On the run in the next transcript that also captured two
variables named =_ModuleTable001_= and =_ModuleTable002_=, which are Lmod's
own base64 bookkeeping.

So a devel module is a faithful record rather than a curated one, and
loading it into a working shell is a decision rather than a habit.
#+end_reveal
#+end_predict
#+begin_src ebtranscript :source "EasyBuild 5.3.1 from PyPI, local workstation, 2026-09-10; system toolchain, so the compiler variables are the host's" :caption "The generated devel module, first lines"
$ head -3 ebtest/software/wobble/1.0/easybuild/wobble-1.0-easybuild-devel
setenv("CC", "gcc")
setenv("CXX", "g++")
setenv("PATH", "/scratch/ebvenv/bin:$HOME/.local/bin:...<the whole of it>")
#+end_src
The docstring in [[https://github.com/easybuilders/easybuild-framework/blob/develop/easybuild/framework/easyblock.py][easybuild/framework/easyblock.py]] describes its usage.
It also describes its limitation.
#+begin_quote
Create a develop module file which sets environment based on the build.
Usage: module load name, which loads the module you want to use.
$EBDEVELNAME should then be the full path to the devel module file. So now
you can module load $EBDEVELNAME.

WARNING: you cannot unload using $EBDEVELNAME (for now: use module unload
`basename $EBDEVELNAME`)
#+end_quote

So the loop is two commands:

#+begin_example
module load QMCPACK/4.4.0-foss-2025a
module load $EBDEVELQMCPACK
#+end_example
After the second step, the shell contains the compilers, the flags, and the =$LIB*= link lines that [[file:16-what-a-toolchain-injects.org][What a toolchain injects]] tabulates for that package's build on this machine.
Two aspects are documented by the code but not mentioned in the documentation.
*It records every environment change, not a curated set.* The implementation iterates =env.get_changes()= and emits a =setenv= for each non‑empty value.
In that run, it included =$PATH= in full and two variables named =_ModuleTable001_= and =_ModuleTable002_=, which are Lmod's own base64 bookkeeping.
No filtering is applied to them.
A devel module provides a faithful record rather than a tidy one.
A =setenv= of =$PATH= should be examined before loading it into a working environment.
*It loads the devel modules of its dependencies.* The load lines are generated by scanning the environment for other =$EBDEVEL*= variables and emitting a load for each.
Loading one devel module imports the build environments of its dependencies.
#+ATTR_EB: :id docs-vs-code-devel :title Documentation and code, on development environments :kind discrepancy
#+begin_detail
Three claims to check rather than inherit, all verified against
EasyBuild 5.3.1 as installed from PyPI on 2026-09-10.

*=--dump-env-script= has no prose documentation.* It appears in the
generated option table at
[[https://docs.easybuild.io/version-specific/eb-help/][docs.easybuild.io/version-specific/eb-help]]
and in release notes, and nowhere else on the documentation site. Its
behaviour here was read from =dump_env_script= and =dump_env_easyblock=
in [[https://github.com/easybuilders/easybuild-framework/blob/develop/easybuild/framework/easyconfig/tools.py][easybuild/framework/easyconfig/tools.py]] and confirmed by running
it.

*The devel module is generated by default and is not the same thing.*
=--dump-env-script= writes the *toolchain's* environment for an
easyconfig, ahead of a build, into the current directory. The devel
module records the environment the build *actually had*, after the fact,
inside the installation. Neither page describes the pair.

*The same environment script is written twice, to different places, by
different code paths.* =dump_env_easyblock= is called from
=dump_env_script= for the file in the working directory, and again from
=main.py= for =reprod/<ec>.env=. The second one is what survives.
#+end_detail

* When it is needed before the build
The command =eb --dump-env-script <easyconfig>= writes =<basename>.env= to the current directory.
The file includes =module load= lines for the toolchain and its dependencies.
The file also includes =export= lines for the build environment.
No build actions occur.
Existing files remain unchanged.
#+begin_src ebtranscript :source "EasyBuild 5.3.1 from PyPI, local workstation, 2026-09-10" :caption "A dumped environment for a system-toolchain recipe, and the refusal to overwrite it"
$ eb wobble-1.0.eb --dump-env-script
Script to set up build environment for wobble-1.0.eb dumped to
wobble-1.0.env

$ cat wobble-1.0.env
#!/bin/bash
# script to set up build environment as defined by EasyBuild v5.3.1 for
# wobble-1.0.eb
# usage: source wobble-1.0.env

# toolchain & dependency modules
# (no modules loaded)

# build environment
# (no build environment defined)

$ eb wobble-1.0.eb --dump-env-script
ERROR: Script(s) already exists, not overwriting them (unless --force is
used): wobble-1.0.env
#+end_src
Both sections are empty.
That outcome is the correct answer, not a failure.
=wobble= uses the system toolchain.
The system toolchain loads no modules.
The system toolchain sets no compiler variables.
Running on a =foss= easyconfig fills both sections.
The two comments indicate that the tool declines to write an empty file.
The tool calls it an environment.
#+ATTR_EB: :id EB-DevEnv-2 :title Archaeology on one install
#+begin_exercise
You have shell access to a machine with an EasyBuild stack and one module
name: =Foo/2.1-foss-2023a=. Nobody who built it is reachable.

Using only what is on that machine, say how you would answer each of
these, and which artifact answers it:

1. Which EasyBuild version built it?
2. Which patches were applied, and what did they change?
3. Which compiler flags did the build get?
4. Would rebuilding it today produce the same thing?

#+begin_solution
1. The build log in =<installdir>/easybuild/=, which records the framework
 version in its header. The easyconfig does not carry it.

2. The archived easyconfig names the patches, and =reprod/= carries the
 easyconfig as parsed. The patch *files* are not necessarily there,
 which is a real gap: if they came from the site's repository and that
 repository moved, the names are all you have.

3. =reprod/<ec>.env=, which is the environment script, or the devel module,
 which records what the build's environment actually became. Both are on
 disk. Loading the toolchain module would not tell you, for the isolation policy's
 reason.

4. Probably not, and the artifacts say why rather than hiding it.
 =reprod/easyblocks/= pins the code that ran, so that much is settled.
 What is not pinned: the framework version (in the log, and installing
 that exact version is on you), the sources (upstream, and possibly
 moved), the dependency installations (modules that may have been
 removed), and the operating system. An honest answer to a user asking
 for a rebuild names those four.
#+end_solution
#+end_exercise

* When somebody else needs it
A dumped script is owned by a single user.
In a team setting, the mechanism uses a module.
EasyBuild provides the generic easyblock =BuildEnv=.
The docstring states: "EasyBuild support for creating a module that loads the build environment flags for the current toolchain".
#+begin_src easyconfig :widget parse
easyblock = 'BuildEnv'

name = 'buildenv'
version = 'default'
versionsuffix = '-foss-2025a'

toolchain = {'name': 'foss', 'version': '2025a'}

moduleclass = 'devel'
#+end_src
No software is installed.
The output is a modulefile.
It sets =$CC=, =$CXX=, =$FC=, =$CFLAGS= and other variables for the named toolchain.
Those variables stay set for the rest of the session.
The RPATH wrapper directory is copied when the site builds with =--rpath=.
Manually compiled binaries are linked like the stack's.
For machines where a modules tool cannot be installed, EasyBuild generates container recipes via =--container-*= options.
An image is built with =--container-build-image= when privileges exist.
Both are stored under =--containerpath=.
#+ATTR_EB: :id env-three-ways :title Five ways to get a build environment :kind reference
#+begin_detail
| Mechanism | Produces | Where it lives | Reproduces |
|---+---+---+---|
| the devel module | a modulefile, generated by default | =<installdir>/easybuild/= | the environment a specific build had |
| =reprod/<ec>.env= | a shell script, written by default | =<installdir>/easybuild/reprod/= | the same, as a script, beside the easyblock source |
| =eb --dump-env-script= | =<ec>.env= to source | the working directory | the toolchain environment for a recipe, before building |
| =BuildEnv= easyblock | an installed modulefile | the module tree | a toolchain's environment, for anyone, versioned |
| =--container-*= | a recipe, and an image | =--containerpath= | the whole machine |

Ordered by how much work they take: the first two are already on disk for
every install the site has made.
#+end_detail

* Doing this on top of EESSI
The stack originates from =/cvmfs= rather than a personal build host.
The issue is addressed by the EESSI‑specific module =EESSI-extend=.
The module loads when =EESSI_SITE_INSTALL= or =EESSI_USER_INSTALL= is set.
EasyBuild configures installation *into* that location atop the mounted stack.
The configuration appears in [[file:11-eessi-somebody-elses-stack.org][EESSI, somebody else's stack]].
=EESSI_EASYBUILD_HOOKS_OVERRIDE= replaces the hooks it uses.
The replacement alters the hooks that give an EESSI build its EESSI shape.
Overriding the hooks permits obtaining a non‑EESSI build.

#+ATTR_EB: :id EB-DevEnv-1 :title Four people who need an environment
#+begin_exercise
Pick a mechanism from [[dive:env-three-ways]] for each, and say what
makes the others worse.

1. A user asks how a module on your site was built, three years after the
 person who built it left.
2. You are debugging why one package's =cmake= picks the wrong MPI, and
 you want to run =cmake= by hand twenty times.
3. A PhD student needs to compile their own code against the toolchain
 the site's VASP was built with, for the next six months.
4. Somebody needs to rebuild a 2023 installation exactly, on a new
 machine, and has the module tree but not the repository.

#+begin_solution
1. Nothing new: =<installdir>/easybuild/= already has the easyconfig, the
 log and =reprod/=. The log names the framework version, the easyconfig
 names the toolchain and the dependencies, and =reprod/easyblocks/=
 contains the code that ran. Those files are the answer to most software
 archaeology on an EasyBuild site, and it needs no tooling.

2. =eb --dump-env-script=, sourced once. The devel module would also
 work if the package is installed, and is one module load rather than a
 file. Either beats a =BuildEnv= module, which is more machinery than a
 twenty-minute investigation needs.

3. =BuildEnv=, named with the toolchain in the =versionsuffix=. Six
 months and a second person means the environment should be
 discoverable and maintained. A dumped script in your home directory is
 neither, and a devel module is tied to one package's build rather than
 to the toolchain.

4. =reprod/=, and then a careful reading of what
 [[dive:reprod-dir]] says is missing from it. You have the recipe, the
 environment script and the easyblock source. You do not have the
 framework version except in the log, the source archives except
 upstream, or the operating system. On a new machine the last one is
 the hard part, which is the argument for building on top of a
 compatibility layer rather than on top of a distribution.
#+end_solution
#+end_exercise

#+begin_keypoints
- Every install already carries the easyconfig, the log, a test report, a
 devel module and a =reprod/= directory holding the easyblock source.
- =module load $EBDEVEL<NAME>= reproduces the environment that build had,
 including =$PATH= and the modules tool's own bookkeeping.
- =eb --dump-env-script= writes the toolchain's environment for a recipe
 before any build, and does not overwrite.
- =BuildEnv= turns a toolchain's environment into a module other people can
 load, and copies in the RPATH wrappers.
- What =reprod/= does not carry: the framework version, the sources, the
 dependency installations, and the operating system.
#+end_keypoints
