#+begin_objectives
1. Install software into a directory the operator owns, on a machine where that operator is
 not an administrator.
2. Read =--show-config= and say where each value came from.
3. Name the three lists involved, and say which one your prefix does not
 touch.
#+end_objectives
EasyBuild does not require administrator rights.
Use a directory owned by the current user.
#+begin_src ebtranscript :source "SURF Snellius, int4 interactive node, 2026-09-09, EasyBuild 5.3.1" :caption "One environment variable, eight paths"

Read the bracketed letters first.
The legend displays the printed configuration model.
Each value originates from the command line, a configuration file, the environment, or a default.
=--show-config= displays the source for each setting.
Precedence follows that order.
A flag overrides a variable.
A variable overrides a file.
Eight settings display =(E)= derived from a single variable.
* And one that did not move
=robot-paths= reports =(D)=.
=robot-paths= remains the default.
=robot-paths= still points at the easyconfigs supplied with the site's EasyBuild.
The prefix sets the output location.
The prefix does not change where EasyBuild *looks*.
[[file:04-the-robot.org][The robot]] provides the explanation.
The two lists are distinct.
The site's easyconfigs stay accessible.
All of the thousands of easyconfigs can be built without copying.
A local directory overrides the site recipe when the site recipe is insufficient.
#+begin_example
export EASYBUILD_ROBOT_PATHS=$HOME/my-easyconfigs:
#+end_example
The trailing colon is The robot's empty element.
Here it is useful: your directory takes precedence, while the site's defaults remain behind it.
If the colon is omitted, the defaults disappear.
* The third list, which is the one people forget
A list untouched by the prefix is not printed by =--show-config=.
The robot queried the module system for installed items via =modtool.available()=.
=MODULEPATH= determines what is considered already built.
Retaining the site's modules on =MODULEPATH= creates one build path.
Removing the site's modules from =MODULEPATH= creates a second distinct build path.
When the site's modules remain on =MODULEPATH=, the default, every dependency already installed by the site is satisfied.
Only a single remaining package is then built.
Nothing else is built.
The process takes twenty minutes instead of two days.
The user's own modules are not present on =MODULEPATH=.
They reside in the user's prefix.
No mechanism places them on =MODULEPATH=.
Therefore, after the build:.
#+begin_example
module use $EASYBUILD_PREFIX/modules/all
#+end_example
Omitting that leads to a confusing symptom.
The build succeeded, the tree exists on disk, yet =module avail= does not list it.
The module system has not been instructed to search for it.
=modules= defaults to =subdir-modules=.
=all= is the location where the default naming scheme places them.
Confirm this by building a component and reading the path printed by EasyBuild.
Alternatively, check =--show-config=.
* The whole path, once
Combine steps on a cluster with EasyBuild loaded as a module.
#+begin_example
module load EasyBuild

export EASYBUILD_PREFIX=$HOME/eb
export EASYBUILD_ROBOT_PATHS=$HOME/my-easyconfigs:

eb --show-config # confirm the four lines above
eb GROMACS-2025.2-foss-2025a.eb -r -D # read the plan first
eb GROMACS-2025.2-foss-2025a.eb -r # then build it

module use $EASYBUILD_PREFIX/modules/all
module avail GROMACS
#+end_example
The =-D= line required, not optional.
The robot's plan depends on the software installed on *this* machine.
It alone indicates whether the plan comprises a single build or ninety.
Read it and decide.
If the site lacks an EasyBuild module, install one in a virtual environment and use it.
It is a Python package; the prefix and robot path function identically thereafter.
#+ATTR_EB: :id EB-Own-1 :title It built, and it will not load
#+begin_exercise
You set =EASYBUILD_PREFIX=$HOME/eb=, ran a build, and it finished. The
tree is on disk under =$HOME/eb/software=. =module avail= does not list
it.

1. Which of the three lists is wrong, and why is it not either of the
 other two?
2. What is the one command that fixes it?
3. A colleague hits the opposite problem: their build takes all night and
 rebuilds forty things the site already has. Which list is wrong for
 them?

#+begin_solution
=MODULEPATH=. The robot path was fine
easyconfig it needed. The prefix was fine
disk where you asked for it. Nothing is broken. You have not told the
module system to look in your prefix.

=module use $EASYBUILD_PREFIX/modules/all=.

Your colleague has the same list wrong in the other direction. Something
has dropped the site's module tree from =MODULEPATH=, so nothing counts
as already built and the whole closure becomes theirs to compile.
The robot restated: the robot path decides what can be found, and
=MODULEPATH= decides what counts as already there. That setting is the one
EasyBuild does not set for you.
#+end_solution
#+end_exercise

* What this costs
Disk resources are consolidated.
Software, sources and build directories reside under a single prefix within a home directory that has a quota.
Set =sourcepath= to a shared download cache when available; clean the build directory.
Time is a factor.
From‑source is [[file:afterword-when-easybuild-is-the-wrong-tool.org][the afterword]]'s trade; costs do not decrease.
Duplication occurs when =MODULEPATH= is incorrect.
Removing the site's modules forces building every dependency; a twenty‑minute job becomes an overnight task.
Support is also affected.
A module located in the prefix belongs to the user.
If it breaks after a system change, no one else will notice.
The same prefix functions with the site's EasyBuild and, when mounted, with EESSI.
If the robot lacks a recipe, generate or bump a =.eb= file; still execute =eb=.

#+begin_keypoints
- Three lists decide what EasyBuild will find: robot path, source path, install path.
- A local prefix does not need a site admin. It does need those three lists set once.
- =--dry-run= first. Then build.
#+end_keypoints
