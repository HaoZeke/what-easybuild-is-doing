* Adding to the module
Four parameters appear in approximate order of frequency of use.
=modextravars= defines additional environment variables.
A package that needs =FOO_DATA_DIR= inside its installation gets it via this parameter.
=modextrapaths= inserts a prefix into a path-like variable.
The mechanism lets a Python package add its =lib/python3.13/site-packages= to =$PYTHONPATH=.
It lets an R package extend =$R_LIBS_SITE=.
=modluafooter= appends raw Lua code to the modulefile.
=modtclfooter= appends raw Tcl code to the modulefile.
It offers an escape hatch for cases not covered by the other parameters.
Use it knowing that it binds the easyconfig to a specific module syntax.
=modaltsoftname= changes the filename used to store the module and keeps the software's original name.
It is uncommon.
It exists.
All four parameters affect what a *user* receives, not what the build receives.
Setting =modextravars= does not help a build that needs an environment variable.
The module is generated in the =module= step after the build has completed several earlier steps.

#+ATTR_EB: :id EB-Module-1 :title Where did that line come from
#+begin_exercise
Using the modulefile above:

1. A user runs =module whatis QMCPACK/4.4.0-foss-2025a= and gets one
 line. Which easyconfig parameter produced it?
2. They then run =module unload QMCPACK= and find HDF5 still loaded.
 Is that a bug?
3. Your package installs data files in =share/mydata= and its binary
 needs =$MYPKG_DATA= to find them. Which parameter, and what is the
 wrong way to do it?
4. A colleague adds =modextravars = {'CC': 'mpicc'}= so builds against
 the module pick up MPI. Why will that not do what they expect?

#+begin_solution
1 is =description=, via =whatis=. Which is the argument for writing a
description that reads as a sentence: it is the one line most users ever
see about your package.

2 is not a bug. =depends_on= is reference-counted, so HDF5 stays loaded
while anything else still depends on it. If nothing does and it stays,
that is worth investigating; if something does, Lmod is doing its job.

3 is =modextravars = {'MYPKG_DATA': '%(installdir)s/share/mydata'}=. The
wrong way is =modluafooter= with a hand-written =setenv=, which works
and ties the easyconfig to Lua, so it breaks for a site using Tcl
modules.

4 will set =$CC= for a user who loads the module, and will do nothing
for a build. A build's environment is constructed in =prepare=, as
[[file:14-the-isolation-policy.org][The isolation policy]] describes, and its =$CC=
comes from the toolchain object rather than from any module. Those builds need
=toolchainopts = {'usempi': True}= in the consuming easyconfig, which is
[[file:16-what-a-toolchain-injects.org][What a toolchain injects]].
#+end_solution
#+end_exercise

#+begin_keypoints
- The modulefile is what a user loads. The easyconfig is how it was built.
- =modextravars= and =modluafooter= write into that modulefile.
- =depends_on= names another module, not a version range.
#+end_keypoints
