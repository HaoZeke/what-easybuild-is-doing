#+TITLE: Chapter 4. The robot
#+OPTIONS: toc:nil num:nil

#+begin_questions
- What is a bare =.eb= filename, if it is not a path?
- Where do the defaults go in =--robot-paths=/my/site:=?
- Which list is the site's, not EasyBuild's?
#+end_questions

#+begin_objectives
1. Say what a bare easyconfig filename is, and what resolves it.
2. Read a =--robot-paths= value and say where the site defaults go in it.
3. Name the three lists the robot consults, and say which one is not
   EasyBuild's to set.
#+end_objectives

The command is this:

#+begin_example
eb GROMACS-2025.2-foss-2025a.eb -r
#+end_example

One file has been named and one package asked for. What arrives is
dozens of modules, most of them never named at the prompt, in an order
that works. The =-r= is what did that. It is short for =--robot=, and this
chapter is about what it does and, more usefully, about where it
looks.

The sample below is a toy robot. It walks a canned universe shipped
with the page, not your site. Change Python from =3.13.1= to =3.11.3=
and watch a dependency drop out.

#+begin_src easyconfig :widget solve :hydrate load :universe canned-foss-2025a
name = 'GROMACS'
version = '2025.2'
toolchain = {'name': 'foss', 'version': '2025a'}

dependencies = [
    ('Python', '3.13.1'),
    ('FFTW', '3.3.10'),
]

builddependencies = [
    ('CMake', '3.31.4'),
]
#+end_src

* A filename is a query

Start with something smaller than it appears. The command passed
=GROMACS-2025.2-foss-2025a.eb= with no path, and the working directory
probably did not contain it.

That works because a bare easyconfig name is not a path, it is a
lookup. EasyBuild resolves it against an ordered list of directories,
the *robot path*, and every dependency it discovers gets resolved the
same way. No difference in kind separates "find the requested easyconfig"
from "find a dependency of the requested easyconfig". Same query,
same path.

Which means the interesting question is never "why can EasyBuild not
find the dependency". It is "what is on the robot path".

* The robot path, and the empty element

The option that sets it is =--robot-paths=. Its default is the
easyconfigs that came with the EasyBuild installation. That is why a
fresh install can build thousands of packages with no extra
configuration.

Now, the part that looks like a typo and is not. The following is a
legal and common way to set it:

#+begin_example
--robot-paths=/my/site/easyconfigs:
#+end_example

That trailing colon is deliberate, and leaving it off inverts the
meaning. Without it the default robot path has been *replaced* with
one directory. EasyBuild can then find none of the thousands of
easyconfigs it came with. With it, EasyBuild searches that directory
first and still has the defaults behind it.

The mechanism is neither a special case nor a parsing quirk. The option
is declared with an action called =add_flex=, and its documentation in
=easybuild/base/generaloption.py= says what that does:

#+begin_quote
similar to add / add_first, but replaces the first "empty" element with
the default
#+end_quote

A colon-separated list =/my/site/easyconfigs:= has two elements, the
second of which is empty. =add_flex= puts the default where the empty
element was. So the colon is not punctuation, it is a *position*: it is
where the defaults are being asked to go. Put it at the front instead,
=:/my/site/easyconfigs=, and EasyBuild searches the site directory last.

Once that is visible the whole option stops being fiddly. The value is
an order, and the blank is the default's place in it.

One related detail, since it decides ties: paths given to =--robot=
itself are placed ahead of =--robot-paths=. The framework does this
explicitly, with the comment "paths specified to =--robot= have
preference over =--robot-paths=".

#+ATTR_EB: :id EB-Robot-1 :title Where do the defaults go
#+begin_exercise
Three settings, one of them wrong for almost every purpose:

: A.  --robot-paths=/my/site/easyconfigs
: B.  --robot-paths=/my/site/easyconfigs:
: C.  --robot-paths=:/my/site/easyconfigs

1. For each, say where EasyBuild looks and in what order.
2. Which one leaves a fresh install unable to find any of the thousands
   of easyconfigs it came with?
3. You want your directory consulted only when the defaults have nothing.
   Which do you pick?

#+begin_solution
The value is a colon-separated list, and the *empty element* is where the
defaults are inserted. That is the whole rule, and everything else
follows from it.

A has one element and no empty one, so the defaults have nowhere to go
and your directory replaces them. That is the answer to question 2, and
it is the common mistake, because the failure looks like EasyBuild having
forgotten every package it ships with.

B has two elements, the second empty, so it reads: yours, then the
defaults. That is the common site layout.

C also has two, the first empty: defaults, then yours. That answers
question 3, and it is the right shape when your directory holds a
fallback rather than an override.
#+end_solution
#+end_exercise

* Why an overlay is the normal case

A site almost always has its own easyconfigs directory in front of the
defaults. The reason is [[file:03-a-pin-is-for-one-generation.org][chapter 3]]'s closing point: an EasyBuild release
carries a fixed set of easyconfigs. Anything merged upstream after that
release is not in it. So the moment a site needs a package newer than
its EasyBuild, it needs somewhere to put that easyconfig. That
somewhere goes first on the robot path.

That freeze is what makes the following two statements true at once,
which is worth holding in mind because it confuses people every time:

- the easyconfig exists upstream, merged, on the development branch;
- the site cannot build it, and its EasyBuild has never heard of it.

Both true. The fix is not to argue with the first one. It is to put a
copy where the robot looks, or to point the robot at the commit that
added it.

* How it decides an order

Given the path, the robot returns an executable order: nothing gets
built before what it needs.

It does not compute that from a finished graph, because it does not
have one. The graph is what it is discovering. =resolve_dependencies=
in =easybuild/tools/robot.py= runs a loop, and that loop's shape
explains most of what =--dry-run= prints.

One pass does this:

1. Ask which easyconfigs are *fully resolved*, meaning every dependency
   they declare is already available. Those go onto the end of the
   order.
2. Treat what just went onto the order as available, since by the time
   it is built it will be.
3. For anything still unresolved, search the robot path for an
   easyconfig that provides the missing dependency, and add it to the
   set being resolved.
4. Repeat.

Step 3 is the one that surprises people. The set of things being
resolved *grows* during resolution, which is why =--dry-run= lists
packages never named and never asked about.

** Available means what the module tool says

Step 1 turns on the word "available", and the function is blunt about
where that comes from:

#+begin_example
avail_modules = modtool.available()
#+end_example

The robot asks your module system what is installed. So the plan is a
function of =MODULEPATH= as much as of the robot path. Those are two
different lists, set in two different ways. A dependency already
installed is satisfied and never appears in the order at all.

Two consequences follow, and both are useful.

A build plan is not portable. Run the same command on a machine with
another set of installed modules and the plan is different, equally
correct.

And =--dry-run= on a well-stocked cluster is short for a reason. It is
not reporting that the package has few dependencies. It is reporting
that most of them are already there.

=-D= / =--dry-run= already retains every dependency and marks each
one =[x]= or =[ ]=. There is no =eb --retain-all-deps=; that name is
an internal argument used by =-D=, =--dep-graph=, and
=--check-conflicts=. =-M= / =--missing-modules= prints only the
absent set.

** What is being rebuilt does not satisfy anything

One detail in the loop is easy to miss and saves an afternoon:

#+begin_example
being_installed = [p['full_mod_name'] for p in easyconfigs]
avail_modules = [m for m in avail_modules if m not in being_installed]
#+end_example

Anything in this run's own list is *removed* from the available set,
even when it is installed. So asking to rebuild a library and something
that depends on it rebuilds both, in that order. The old library does
not satisfy the dependent.

There is a matching escape hatch. A dependency marked as an external
module has no easyconfig, so the robot does not search for one. It
still requires the module to be available. If it is not, the resolve
loop ends with =Missing modules for dependencies marked as external
modules=. That is how a site tells the robot about a module EasyBuild
did not build, not how it pretends the module exists.

** The order is not unique

Any topological order of the discovered graph is correct, and EasyBuild
does not promise a particular one. The list from =--dry-run= is *an*
answer rather than *the* answer, so diffing two of them across versions
shows churn that means nothing. Chapter 2's sibling toolchains are the
same fact one level down.

** And the hierarchy filters the candidates

The hierarchy from [[file:02-a-toolchain-is-a-hierarchy.org][chapter 2]] decides what step 3 is allowed to find. A
candidate counts as a candidate only when its toolchain belongs to the
package's hierarchy.

That filter is where the two chapters meet, and it produces the most
frustrating class of robot failure. The module is installed.
=module avail= lists it. And the robot says it cannot find it.

The robot is not lying. It is reporting that nothing *in the
package's hierarchy* provides that dependency. A module built with a
toolchain outside that hierarchy is invisible rather than rejected.

#+ATTR_EB: :id EB-Robot-2 :title The same command, two different plans
#+begin_exercise
You run the same command with =-D= on two machines, from the same
easyconfig and the same robot path:

: eb GROMACS-2025.2-foss-2025a.eb -r -D

On the cluster it lists three things to build. On your laptop it lists
ninety.

1. What differs, given that the robot path is the same?
2. Which flag makes the cluster print the ninety as well, and when would
   you want that?

#+begin_solution
=MODULEPATH=. The robot asks the module system what is installed, through
=modtool.available()=, and treats anything already there as satisfied.
The cluster has eighty-seven of those dependencies installed and your
laptop has none.

So a build plan is a property of the machine as much as of the
easyconfig, and it does not travel between them. The robot path decides
what can be *found*; =MODULEPATH= decides what counts as already *built*.

=-D= already retains every dependency and marks each one. There is no
=eb --retain-all-deps=. Use =-D= when the question is the full
closure, and =-M= when the question is what is absent on this
machine.
#+end_solution
#+end_exercise

* Ask before the build

The robot reports what it decided without doing any of it:

#+begin_example
eb GROMACS-2025.2-foss-2025a.eb -r -D
#+end_example

=-D= is =--dry-run=. The resolved list comes back, with a marker beside
each entry saying whether it is already installed or would be built.

Read it before every non-trivial build, for one specific reason. The
command as typed hides the difference between "this will install two
things" and "this will install ninety things". That is the difference
between a coffee and an afternoon.

It is also the fastest way to catch a dependency resolving to a version
that was not expected. That happens most often when a site overlay shadows
an upstream easyconfig with the same name.

* Three lists, and a loop

The robot consults three lists, and confusing them is most of what goes
wrong:

| List | Set by | Decides |
|---+---+---|
| the robot path | =--robot-paths=, empty element for the defaults | which easyconfigs can be found |
| =MODULEPATH= | your module system, not EasyBuild | what counts as already built |
| the toolchain hierarchy | chapter 2, computed | which found candidates are eligible |

Around those it runs a loop rather than a graph traversal. Take
whatever is fully resolved, treat it as available, search the path for
what is missing, repeat. The set being resolved grows as it goes, which
is why =--dry-run= names packages never asked for.

Two consequences worth carrying. A plan is not portable, because the
second list differs per machine. And anything in this run's own list
stops counting as available, so rebuilding a library and its dependent
rebuilds both.

Read =-D= before every non-trivial build. It is the only thing that
distinguishes one install from ninety.

constraint and behaves like a label.
