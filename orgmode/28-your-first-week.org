#+TITLE: Chapter 28. Your first week on somebody's stack

#+OPTIONS: toc:nil num:nil

#+begin_objectives
1. Take a "bump this package" ticket from the request to a built module,
   in the order that finds the problems early.
2. Say what your site's pipeline adds on top of =eb=, and find those parts
   in a repository not seen before.
3. Diagnose a failure that a build host reports as green.
#+end_objectives

Everything so far has been a mechanism. This chapter is the job.

Three tasks, all real, all of the kind handed to somebody in their first
month. Each is written as a sequence that can be followed, with the point where
a first-timer goes wrong marked, because the interesting part of each one
is not the fix.

* What stands between the operator and eb

Nothing in this chapter is about EasyBuild's defaults, because no site
runs them. Before the first task, find these five things in your site's
repository. Every site has them, under different names, and a newcomer who
finds them in the first hour stops guessing.

*The recipes.* One directory per initial in most site repositories,
matching upstream's layout, with patches beside the easyconfig that needs
them.

*The build list.* A file per stack generation naming what gets built, in
order, one entry per line, often with per-entry flags. A human edits that
file to schedule a build; the easyconfig alone schedules nothing.

*The pipeline.* Something reads that list and calls =eb= once per entry,
per architecture, with the site's configuration: install prefix,
=--optarch=, CUDA compute capabilities, module naming, hooks. Read the
whole of it once. Every difference between your site and this book's
transcripts starts there.

*The hooks.* [[file:09-a-hook-changes-a-file-you-are-not-reading.org][Chapter
9]]'s subject, and the reason a recipe can say one thing and the build do
another. Find the directory, and find which hook applies to the package
about to be touched.

*The templates.* Starter easyconfigs, one per easyblock shape. Copy the
site's template rather than upstream's example, and your first
contribution comes out looking like everybody else's.

#+ATTR_EB: :id site-questions :title Five questions to answer before your first build :kind reference
#+begin_detail
Write the answers down; they are needed all week.

| Question | Where to look |
|---+---|
| Which generation am I building into, and which is in production? | the build lists, and the install prefix each pipeline uses |
| Which architectures does one entry become? | the pipeline's per-architecture configuration |
| What does a build inherit that is not in the easyconfig? | =eb --show-config=, then the hooks directory |
| How do I schedule one package rather than the whole list? | the pipeline's test or single-entry mode |
| Where do the logs of a failed build end up, and for how long? | the pipeline's output directory, and its retention |

The last one decides whether a failure tomorrow can be diagnosed. On a
site that discards build directories nightly,
[[file:20-reading-a-failed-build.org][chapter 20]]'s advice about
=config.log= has a deadline.
#+end_detail

* Task one: the bump that was verified four ways and still failed

The request: *"this package is pinned to a development commit, because no
release carried the feature the group needs. Release 4.4.0 has it. Move
the four recipes onto the release."*

What was done, in order, before anything was built:

1. Four recipes copied and pointed at the release archive.
2. Four lines added to the current generation's build list.
3. =eb-stack recipe lint=: clean.
4. Dependency resolution: clean.
5. The SHA256 of the release archive, compared against the one written
   into the recipes: identical.
6. A diff of build flags, dependencies and sanity checks against the
   previous version's recipes: identical.

All four builds then failed, before compiling anything:

#+begin_example
Specified start dir /scratch/build/.../qmcpack-4.4.0/qmcpack does not exist
#+end_example

*Where it went wrong: =start_dir= was carried across.* It had been correct
for as long as the recipe built from a git commit, because EasyBuild
archives a clone under the repository's name, so the sources were in
=qmcpack/=. The release tarball extracts to =qmcpack-4.4.0/= with
=CMakeLists.txt= at the top, and
[[file:20-reading-a-failed-build.org][chapter 20]]'s descent rule then
resolves a relative =start_dir= under that.

The method failure is the more useful half. The verifying diff in step 6
*deliberately excluded the source block*, on the grounds that the source
block is the thing meant to change. =start_dir= is not in that block, and
it is a function of it. So six checks passed, each of them correctly, and
not one of them could see the fault.

The general form: *a version bump is a change of source, and every
parameter that describes the shape of the source has to be re-read.*
=start_dir=, patch strip levels, =sanity_check_paths=, anything holding a
directory name.

#+ATTR_EB: :title Before you look it up
#+begin_predict
The version has been bumped, a checksum injected, and the build fails in
the =configure= step with a path that does not exist. Nothing has yet
opened the log.

Which two commands run first, and which one of them a dry run
could have replaced?

#+begin_reveal
=eb --last-log= and then =tar tzf= on the new archive.

Neither is replaceable by a dry run, and that is the point: =eb -x= never
extracts anything, so a parameter that names a directory the archive does
not contain looks fine under it. The archive listing is the only thing
that settles it.

If =--force= or a rebuild was the first move, that is the reflex worth
losing: nothing about this failure is stale state.
#+end_reveal
#+end_predict

* Task two: the check that was switched off over the defect it found

The request, as it arrived twenty days late: *"the GPU build of this code
will not start."*

#+begin_example
vasp_std: error while loading shared libraries: libnvJitLink.so.13:
cannot open shared object file: No such file or directory
#+end_example

The whole sequence, because the sequence is the lesson:

1. A production run installs the package on a vendor toolchain. After two
   hours and sixteen minutes, the RPATH sanity check fails:
   =Library libnvJitLink.so.13 not found=.
2. =skipsteps = ['sanitycheck']= goes into the recipe, with a comment
   naming the newer CUDA tree inside the vendor toolchain. The reasoning:
   the check reports a defect this package cannot fix.
3. A second recipe, for another version of the same package on the same
   toolchain, is added and inherits the =skipsteps=.
4. Twenty days pass. A user loads the module and gets the loader error
   above.
5. =skipsteps= comes out of both recipes.
6. A root cause is published, and then *retracted*, having been checked
   from a login node.
7. The root cause is re-established, on the hardware, and the toolchain's
   own recipe is fixed: =postinstallcmds= relinking the unversioned
   =math_libs= and =comm_libs= entries at the CUDA version the module
   declares.
8. A temporary =--rebuild= goes on the build-list lines for everything
   built against the broken toolchain, and comes off once the results are
   checked on a node of each architecture class.

Three separate mistakes are in that list, and only one of them is the
symlink.

*Switching the check off moved the discovery to a user.* Step 2's
reasoning was true in both halves: the check was reporting a real defect,
and no change to this package could repair it. The conclusion did not
follow. The check was carrying information about the *toolchain*, and
deleting the report left the toolchain broken and the package shipping.
[[file:23-testing.org][Chapter 23]].

*The workaround spread while the defect was hidden.* Step 3 is what a
skipped check costs beyond one package: the next recipe copied the
workaround along with everything else, because copying a recipe is how
recipes get written.

*The retraction is the part to learn from.* Step 6 happened because
=/sw/arch= resolves to the architecture of the node reading it, and the
binary's own [[dive:term-rpath]] carries that prefix. So =ldd= on the GPU
binary, run from a login node, reports zero missing libraries. Pointing at
the other architecture's tree by its full path does not rescue the test
either: the RPATH inside the binary still resolves against the node
the command runs on.

*Where a first-timer goes wrong: they publish step 6.* A clean check is
persuasive, it is cheap, and on a heterogeneous machine it is evidence
about the node it ran on and nothing else.

The general form: *a claim about library resolution has to be measured on
the architecture that will run the binary.* The first command in that
diagnosis is =readlink -f= on the per-node path, on the node the user's
job ran on.

And the thing to take from step 8: a rebuild flag added to fix a batch is
temporary, so it needs a named owner and a date, or it becomes permanent
and nobody remembers what it was for.

#+ATTR_EB: :id EB-Week-2 :title The commit you would write
#+begin_exercise
You have just fixed the toolchain from task two: the unversioned library
directories now point at the CUDA version the module declares, set in
=postinstallcmds=.

Write the commit message. Specifically decide:

1. What has to be in it for the person who reads it in a year.
2. Whether the rebuilt packages need anything, and how you would say so.
3. What you would say about the twenty days, and to whom.
4. Which of these belongs in the commit and which belongs somewhere else:
   the loader error, the architectures affected, how you measured it, the
   ticket, and the fact that a sanity check had been switched off.

#+begin_solution
1. What was wrong, in one line a search will find: the unversioned
   =math_libs= and =comm_libs= entries pointed into the newer CUDA tree
   the same tarball carries. Then why the fix is where it is:
   =postinstallcmds= runs before the sanity check, so the check that had
   been failing can pass honestly.

2. Yes: anything built against the broken toolchain linked the wrong
   library and has to be rebuilt. Say which packages, and say that the
   rebuild flag is temporary and who removes it. A temporary flag with no
   named owner becomes permanent.

3. That the check had been switched off, that it was reporting this
   defect, and that the twenty days are the cost of that decision rather
   than of the defect. It goes to whoever will make the same call next
   month, which means the commit message and the team's notes, not the
   ticket. The user gets a working module and a date, not an autopsy.

4. In the commit: the error string, because it is what the next person
   will search for; the architectures affected, because that is the shape
   of the bug; how you measured it, in one line, because a claim about
   library resolution is only as good as the node it was made on. Not in
   the commit: the ticket reference on its own, which ages out, and the
   detail of the earlier retracted diagnosis, which belongs in the notes
   where somebody can read the whole sequence.
#+end_solution
#+end_exercise

* Task three: a user says a module is broken and the report cannot be reproduced

The request: *"this module works for me and fails for them"*, which is the
commonest ticket in this job and the one with the most wrong answers.

The sequence is a bisection over the four things that differ:

1. *Which architecture.* Resolve the per-node path on their node and on
   yours. Different trees mean different installs, and the module name
   reports nothing.
2. *Which module.* Have them send =module list= rather than the name they
   think they loaded. A different generation on =MODULEPATH= is the second
   most common answer.
3. *Which environment.* =eb --show-config= on your side, their shell's
   environment on theirs. A site hook or a user's own =MODULEPATH= is
   [[file:09-a-hook-changes-a-file-you-are-not-reading.org][chapter 9]].
4. *Which node.* A GPU library, a filesystem client, a fabric: all
   host-provided, none in the module.
   [[file:26-the-same-stack-somewhere-else.org][Chapter 26]]'s last
   section is this list.

*Where a first-timer goes wrong: they answer the ticket after step 3.*

Three of the four checks pass, the module looks identical, and the
temptation is to reply that it works. The fourth is where the difference
tends to be, and a reply that closes a ticket names the node and the
architecture it was tested on.

** A pipeline's summary can be empty for two different reasons

One more trap, from a bump that went green on three architecture classes
and red on one, with the same prebuilt archive.

A pipeline that summarises a run typically fills a field like
=EasyBuild log:= by grepping its own output for the line =eb= prints at
the end, =Results of the build can be found in the log file(s)=. =eb=
prints that line on failed builds too. So an *empty* log field does not
mean "no information": it means =eb= never got as far as printing it,
which puts the failure before the easyconfig was processed at all, in the
fetch phase.

And a field like =Last successful build:= reporting *never* carries no
signal for a line just added, because it is a search of previous
runs for that filename and your filename has never appeared.

Read your pipeline's summariser once, and find out which of its fields
can be empty for a reason other than absence.

#+ATTR_EB: :id first-week-habits :title Four habits that shorten the week :kind reference
#+begin_detail
1. *State where a result came from.* Every claim about a build
   carries a machine and an architecture, in the ticket and in the commit
   message. This book's transcripts do it for the same reason.
2. *Read the archive, not the diff.* A version bump is a change of source.
3. *Do not switch a check off to make a build pass.* A failing check on a
   package that cannot be fixed is a report about something else.
   [[file:23-testing.org][Chapter 23]].
4. *Write the diagnosis down where the next person will look.* The
   install already carries the easyconfig, the log and =reprod/=; what it
   does not carry is why that choice was made.
#+end_detail

#+ATTR_EB: :id EB-Week-1 :title Your actual first ticket
#+begin_exercise
A user writes: "Could you install version 6.5.1? We need the GPU build,
and the version you have is too old for our workflow."

Write the plan before you type anything. Specifically:

1. The first four things you find out, and from where.
2. Which of the three tasks above this is, and which parts of the other
   two it also contains.
3. The two failures you expect, and the check that would catch each one
   before a user does.
4. What the reply will carry, and what it will omit until
   you have measured it.

#+begin_solution
1. Whether upstream has an easyconfig for 6.5.1 at all
   (=eb --search=); which toolchain the GPU build needs and whether your
   site has it at this generation; what the site's current version was
   built with, from the archived easyconfig in its install directory; and
   whether the licence covers this group, which is the question that
   blocks everything else and has nothing to do with EasyBuild.

2. Mostly task two, with task one inside it: a version change *and* a
   toolchain choice. If the toolchain is new to the site it is also a
   stack decision, and that is somebody else's call as much as yours.

3. A source-shape failure, caught by listing the archive and re-reading
   every parameter that names a directory. And an architecture-specific
   runtime failure, caught only by running the binary on the target
   hardware; the build host passing tells you about the build host.

4. The reply says which version, which toolchain, which architectures it
   was built for, and on which architecture it was actually run. It does
   not say "it works" on the strength of a login-node check, and it does
   not promise a date before the toolchain question is settled.
#+end_solution
#+end_exercise

#+begin_keypoints
- A site's pipeline, build lists and hooks are what stand between an
  easyconfig and a module; find all three before your first build.
- A version bump is a change of source: re-read every parameter that
  describes the shape of the archive.
- A dry run cannot see a fault that depends on the contents of an archive.
- On a heterogeneous system, measure library resolution on the
  architecture that will run the binary, not on the one underfoot.
- Every claim about a build carries the machine and the architecture it
  was measured on, or it is not a claim.
#+end_keypoints
