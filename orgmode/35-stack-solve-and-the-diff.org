The =package plan= evaluates *one package's* profiles against a robot tree.
The annual bump of a site stack raises another question.
With many roots and a single target generation, the system asks which jointly consistent set is built.
It also asks for the build order of the set and the changes since the previous year.
The command is =stack solve=.
* A policy for many roots
The fixture policy at =fixtures/gromacs_2025_to_next/policies/prefer_newer.json= represents the smallest interesting case.
#+begin_example
{
 "toolchain": {"name": "foss", "version": "2025b"},
 "roots": ["GROMACS"],
 "root_priority": ["GROMACS"],
 "pins": [],
 "forbid": [],
 "objective": "prefer_newer",
 "require_upgrade": {"name": "GROMACS", "relative_to_baseline": true}
}
#+end_example
Roots and each declared runtime and build requirement are co‑selected.
=root_priority= stabilizes a multi‑root solve according to list order.
Pins employ EasyBuild‑shaped requirements such as = ==0.3.24= and = >=1.14=.
=forbid= accepts either a package name or a full easyconfig path.
=require_upgrade= with =relative_to_baseline= fails if the baseline package is absent or if no newer jointly feasible candidate exists.
This JSON is not the TOML =--stack-policy= of Inspect; it writes a work queue rather than a recipe.
Package commands accept TOML preferences for a single product.
Whole‑stack solve uses this JSON schema.
Mixing the files produces a parse error rather than a clever override.
* Four artifacts from one solve

#+begin_example
eb-stack stack solve \
 --easyconfigs fixtures/gromacs_2025_to_next/easyconfigs \
 --policy fixtures/gromacs_2025_to_next/policies/prefer_newer.json \
 --baseline-easyconfigs fixtures/gromacs_2025_to_next/easyconfigs \
 --lock-out stack.lock.json \
 --sbom-out stack.cdx.json \
 --build-list-out build.list \
 --stack-diff-out stack.diff.md
#+end_example
=--easyconfigs= may be specified multiple times.
Later paths replace earlier ones when name, version, toolchain, and versionsuffix match.
A site‑only package is added to the universe.
=--stack-diff-out= requires =--baseline-easyconfigs=.
Omitting the baseline causes an error instead of a silent skip.
=stack.lock.json= follows schema 1.
=toolchain= denotes the policy target.
=packages= is the co‑selected set ordered by name; each entry includes its own toolchain, an optional versionsuffix, and an =easyconfig_path=.
=solver.engine= is set to =resolvo_cdcl_sat=.
=build.list= lists one easyconfig path per line, arranged topologically over the co‑selected stack with ties resolved by package name.
An empty lock produces an empty file.
A sequential =eb= loop, a Jenkins step, or =xargs -n1= reads the file.
The file is not markdown nor an SBOM.
=stack.diff.md= is the pull‑request body.
Each co‑selected package is labeled =unchanged=, =added=, =removed=, or =version-bumped= relative to the baseline.
#+begin_example
# Stack diff

Baseline (`foss-2025a`) -> solved (`foss-2025b`).

## Summary

- **unchanged**: 1
- **added**: 0
- **removed**: 0
- **version-bumped**: 3
#+end_example
The file =stack.cdx.json= generated *during* solve retains the candidate graph.
Dependency edges.
The alternative SBOM command does not include them.
#+begin_example
eb-stack stack sbom --lock stack.lock.json --out stack.cdx.json
#+end_example
A lock‑only SBOM cannot rebuild edges and does not create them.
Apply =--sbom-out= to =stack solve= while the graph remains in memory.

#+begin_keypoints
- =stack solve= is the multi-root annual-bump solver. Its policy
 is JSON. The package command's =--stack-policy= is TOML. They
 are not interchangeable.
- =build.list= is the install order. =stack.diff.md= is the pull
 request. =stack.lock.json= is the Resolvo assignment.
- A lock-only SBOM has no dependency edges. Edges are written
 only when =--sbom-out= is passed to =stack solve=.
#+end_keypoints
