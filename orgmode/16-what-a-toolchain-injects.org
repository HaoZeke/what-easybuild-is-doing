#+TITLE: Chapter 16. What a toolchain injects

#+OPTIONS: toc:nil num:nil

#+begin_objectives
1. Say which environment variables a toolchain sets during a build, and

2. Read a =toolchainopts= dictionary and say what each option changes.
3. Say what =optarch= does and why it decides where a binary can run.

[[file:02-a-toolchain-is-a-hierarchy.org][Chapter 2]] was about which
dependencies a toolchain makes visible. This chapter is the other half:
what it does to the compiler.

* The variables, and where they are not

[[file:14-the-isolation-policy.org][Chapter 14]] measured the surprising
part, and it is worth restating because everything here follows from it.
Loading a toolchain module gives =EBROOTFOSS= and =EBVERSIONFOSS=.
It does not give =$CC=.

The compiler variables are set by EasyBuild's *toolchain object*, during
=prepare=, inside the build. A =foss= build gets, among others:

| Variable | What it holds |
|---+---|
| =$CC=, =$CXX=, =$FC=, =$F90= | the compiler drivers |
| =$MPICC=, =$MPICXX=, =$MPIF90= | the MPI wrappers |
| =$CFLAGS=, =$CXXFLAGS=, =$FFLAGS= | optimisation and architecture flags |
| =$LDFLAGS=, =$CPPFLAGS= | library and include paths for every dependency |
| =$LIBBLAS=, =$LIBLAPACK=, =$LIBSCALAPACK=, =$LIBFFT= | the link lines for the numerical libraries |

That last row is the reason a =foss= easyconfig rarely names a BLAS. The
toolchain knows which BLAS it is, and hands the build a link line for it.
An easyconfig that hardcodes =-lopenblas= is describing one toolchain and
will be wrong on the next.

The practical consequence is the one from chapter 14. To reproduce a
build's environment, loading its toolchain is not enough;
=eb --dump-env-script= is needed, which is
[[file:24-development-environments.org][chapter 24]].

* toolchainopts is a dictionary of switches

#+begin_src easyconfig :widget parse
name = 'example'
version = '1.0'
toolchain = {'name': 'foss', 'version': '2025a'}
toolchainopts = {'usempi': True, 'openmp': True, 'pic': True}
#+end_src

Each key changes what the toolchain object puts in those variables.
=foss= in EasyBuild 5.3 accepts about thirty, and the list is:

    ieee: Adhere to IEEE-754 rules (default: False)
    lto: Enable Link Time Optimization (default: False)

    optarch: Enable architecture optimizations (default: True)
    pic: Use PIC (default: False)
    shared: Build shared library (default: False)
    static: Build static library (default: False)

    usempi: Use MPI compiler as default compiler (default: False)
    verbose: Verbose output (default: False)
    veryloose: Very loose precision (default: False)

Four of them account for most of what appears in real easyconfigs.

=usempi= makes =$CC= the MPI wrapper rather than the bare compiler. A
package whose build system does not know about MPI wrappers, and just
uses =$CC=, gets MPI this way. Reach for it when the software is parallel
and its configure script has no =--with-mpi=.

=openmp= adds the compiler's OpenMP flag. Needed when the source has
=#pragma omp= and the build system does not add the flag itself, which is
more common than it should be.

=pic= adds =-fPIC=. Needed when something links a static library into a
shared one, and the error without it names a relocation rather
than anything recognisable.

The precision family, =strict= through =veryloose=, is the one to leave
alone unless there is a reason. It changes floating-point semantics, which
changes results. A physics code that specifies =strict= is making a
claim about its own numerics, and changing it silently changes the
science.

* optarch decides where the binary runs

=optarch= is on by default, and it is the option with the largest
consequences.

On, the compiler is told to optimise for the microarchitecture it is
running on: =-march=native= or the toolchain's equivalent. The binary is
faster and it may use instructions that a different processor in the same
cluster does not have.

That is the mechanism behind
[[file:06-what-installed-means.org][chapter 6]]'s per-architecture install
trees. A site with mixed hardware does not keep separate trees out of
tidiness; it keeps them because =optarch= produced binaries that are not
interchangeable.

Two ways a site controls this.

=--optarch= on the command line sets the flag globally. A site can then
build for a named baseline rather than for whatever node the build landed
on.

And =toolchainopts = {'optarch': False}= turns it off for one package.
Reach for that when a package is known to miscompile under aggressive
optimisation.

An easyconfig that needs =optarch: False= should say why in a comment.
It is a claim about the software rather than about the site, and the next
person to read it will otherwise assume it was cargo-culted.

#+ATTR_EB: :id EB-Toolchainopts-1 :title Four errors, four options
#+begin_exercise
Four build failures, each fixed by one =toolchainopts= key.

1. =undefined reference to `omp_get_num_threads'=
2. =relocation R_X86_64_32S against `.rodata' can not be used when
   making a shared object=
3. =mpi.h: No such file or directory=, from a Makefile that compiles with
   =$(CC)=
4. The build succeeds on the build host and dies with =Illegal
   instruction= on an older node in the same cluster.

Give the key for each. Then say which of the four is not really a
toolchain question at all, and what you would rather do about it.

#+begin_solution
1 is =openmp=. The source uses OpenMP and nothing added the flag.

2 is =pic=. Something static is being linked into something shared.

3 is =usempi=, so =$CC= becomes the MPI wrapper and =mpi.h= is on the
include path. The alternative is patching the Makefile to use =$(MPICC)=,
which is more honest and more work.

4 is =optarch=, and it is the one that is not really a toolchain
question. Setting =optarch: False= for this package would fix the symptom
by making the binary slower everywhere, to accommodate a node it was
never built for. The real answer is the site's: either build per
architecture, as chapter 6 describes, or set a site-wide =--optarch=
baseline that every node can run. A per-easyconfig fix for a site-wide
hardware fact is the wrong layer.
#+end_solution
#+end_exercise
