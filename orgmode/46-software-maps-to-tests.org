Portable tests not listed for their software do not run when the software is merged.
EESSI provides a mapping file as its answer.
CSCS provides a directory of checks and a daily invocation as its answer.
Both implement the same concept.
The suite names are collected in one location.
The collection determines which tests a package requires.
* EESSI: three uses, one suite
The writing-tests page lists three reasons the suite exists.
One reason is a contribution.
New software is being added to EESSI.
The mapping says which tests now apply.
The bot runs them on the architecture the build targeted, through [[https://github.com/EESSI/software-layer-scripts/blob/main/bot/test.sh][bot/test.sh]].
Another reason is a nightly.
The same tests run on a set of clusters, looking for a performance regression.
A third reason is an end user.
The end user runs one test or the whole suite to see whether this machine plus this EESSI mount actually runs.
Those are three filters over one tree, not three suites.
The =CI= tag from Parameters multiplies the suite, acting as the contribution filter: Crambin, five minutes, eight cores.
The nightly drops the tag and keeps the HECBioSim ladder.
The end user passes =--name GROMACS= or does not.
The mapping lives in EESSI/software-layer-scripts, not next to the test classes.
Testing and the four things it can mean already named it: [[https://github.com/EESSI/software-layer-scripts/blob/main/tests/eessi_test_mapping/software_to_tests.yml][software_to_tests.yml]].
Adding GROMACS to the stack without a line in that file causes a green build to ship a module that the suite will not touch.
The generalisable rule is that a test has a location, and a result without its location is not a result.
The mapping is that location, written down.
Available tests in the public suite include GROMACS (six HECBioSim systems, implemented on top of ReFrame's =hpctestlib=), TensorFlow (the multi‑worker Keras tutorial), CP2K, OpenFOAM and the OSU microbenchmarks.
Each class lives in [[https://github.com/EESSI/test-suite][EESSI/test-suite]] under =eessi/testsuite/tests/apps/=.
The mapping connects a module name to those classes.
* CSCS: config, checks, CI
The CSCS suite =eth-cscs/cscs-reframe-tests= provides the layout cited in the official ReFrame README, which is the most complete public tree.
Three directories each execute a distinct job.
#+begin_example
cscs-reframe-tests/
├── config/ the machine
├── checks/ the tests
├── ci/ how the site invokes them
├── uenv_checks/ the same idea for uenv stacks
└── portable_tests.md
#+end_example
List all information the suite knows about on a CSCS system.
#+begin_example
reframe -C cscs-reframe-tests/config/cscs.py \
 -c cscs-reframe-tests/checks/ -R -l
#+end_example
=-C= denotes the configuration file that is the machine.
=-c= denotes the check path.
=-R= causes recursion.
=-l= causes listing.
The daily run uses the command with =-r= instead of =-l= from [[https://github.com/eth-cscs/cscs-reframe-tests/tree/master/ci][ci/]].
A site copying this layout does not need EESSI.
The site must have a configuration file describing its partitions, a directory of tests that do not name those partitions, and a nightly job that runs the listing.
=portable_tests.md= in that tree defines the written rule for what a check may assume.
EESSI's mixin implements the same rule, enforced in code.
* LUMI, CSC and why this is a part
The CSC Finland computing‑environment course contains ten topics on using Puhti and Mahti, including modules, batch jobs, Allas and containers.
The course is not a ReFrame course.
LUMI's user documentation covers the same material for that machine.
The ReFrame course consists of CSCS's webinar, the official tutorial, and EESSI's writing‑tests page.
These pages are ReframeReader rather than a subsection of Testing.
The fourth kind of testing has its own layout. The centres that run
it teach it as an independent course.
#+ATTR_EB: :id EB-ReFrame-46-1 :title Which filter
#+begin_exercise
Three requests. For each, say which invocation, and whether
the mapping file has to contain the software yet.

1. A pull request adding =GROMACS/2024.4-foss-2023b= to
 EESSI. The reviewer asks for the five-minute case.
2. The nightly on a CPU partition, every GROMACS HECBioSim
 system the suite knows.
3. A user on a laptop with the EESSI CernVM-FS client,
 asking whether =mpi4py= imports and reduces.
#+begin_solution
1. =reframe --name GROMACS --tag CI -r=, after the mapping
 names GROMACS. Without the mapping entry the bot has
 nothing to run, and the PR is a build without the
 fourth kind of test. The mapping has to contain it
 *in the same change*.

2. =reframe --name GROMACS -r= on that partition, no =CI=
 tag. The mapping already contains it; the nightly is
 not the time to add the line.

3. =reframe --name EESSI_MPI4PY -r= against a configuration
 that describes the laptop (local scheduler, the EESSI
 modules system). The mapping is irrelevant to a human
 who named the test. =find_modules= supplies the module
 that the client actually mounted.
#+end_solution
#+end_exercise

#+begin_keypoints
- A mapping file is how a new module inherits tests. A
 missing line is a silent skip the next morning.
- EESSI's suite is one tree with three filters:
 contribution (=CI=), nightly, end user.
- CSCS lays out [[https://github.com/eth-cscs/cscs-reframe-tests/tree/master/config][the config tree]], [[https://github.com/eth-cscs/cscs-reframe-tests/tree/master/checks][the checks tree]], [[https://github.com/eth-cscs/cscs-reframe-tests/tree/master/ci][the ci tree]]. The machine,
 the tests, and the invocation stay apart.
- CSC's computing-environment course is not this course.
 ReFrame is taught as its own unit, which is why it is
 a part of this book.
#+end_keypoints
