3. Say what a green build on your own host establishes about the other

There is a directory on a lot of clusters, and on a surprising number
of laptops, that nobody at the site built.

EESSI's workforce is funded in large part by MultiXscale, a EuroHPC
Centre of Excellence (CECAM × EESSI). CASTIEL 2 is the tutorial
portal, not the build farm. The EFP Federated Software Catalogue
(CSC.fi with Ghent) is a 2026 catalogue layer on top. Compute Canada
is the design parent of the three-layer split. A first week on a
EuroHPC box is often EESSI via that catalogue, not a local EasyBuild
prefix.

* The stack is a filesystem

#+begin_example
ls /cvmfs/software.eessi.io/versions/
#+end_example

Those are versions of a whole scientific software stack: compilers,
MPI, the usual suspects, tuned per microarchitecture, delivered on a
filesystem that arrived over HTTP. EESSI is not installed. It is
mounted, or the session is on a machine where somebody already did.

Pick one and initialise it:

#+begin_example
source /cvmfs/software.eessi.io/versions/2025.06/init/lmod/bash
#+end_example

That yields a compatibility layer, a module tree, and a set of
toolchains, without an install step and without a maintainer having
approved anything.

Two warnings belong right here, before anything else, because both cost
real time.

The first is about that =ls=. List the versions directory, and confirm a
version is real before using it:

#+begin_example
ls /cvmfs/software.eessi.io/versions/<ver>/init/lmod/bash
#+end_example

A listed version can be an unpopulated placeholder with no =init/= at
all. Descending into one speculatively can wedge the filesystem client
for every user on the host. The lookup neither resolves nor errors, and
readers pile up in uninterruptible state where a timeout cannot reach
them. List first. Confirm. Then use.

The second is the generation question, and it decides whether the rest
of this chapter applies at all.

* Check the generation before planning anything

The compatibility layer lags the newest EasyBuild toolchain generation.
So a version of EESSI carries some set of top-level toolchains, and your
easyconfig names one particular generation, and those two facts have to
agree.

When they do not, EESSI reports the mismatch, and an opt-in is available:

#+begin_example
export EESSI_SITE_TOP_LEVEL_TOOLCHAINS_2025_06='[{"name": "GCCcore", "version": "15.2.0"}]'
#+end_example

Setting that makes EasyBuild *plan* the build. Read what the plan says
before the script runs. When the generation is absent from the compatibility
layer, every dependency comes back skipped. The run then opens by
bootstrapping the compiler itself, and downloads a couple of hundred
megabytes of GCC to do it.

Do not do that. Bootstrapping a whole generation into a user prefix
duplicates what EESSI's own build bots do centrally. It is also a long
way round to a stack that cannot be shared. A generation gap means "not yet
on this EESSI version", which is a finding rather than a failure.

* Installing on top, with EESSI-extend

EESSI carries a module that configures EasyBuild for installing onto
the stack. The build bots use the same one, so this path matches what
the bot will do:

#+begin_example
source /cvmfs/software.eessi.io/versions/2025.06/init/lmod/bash

export EESSI_USER_INSTALL=$HOME/eessi/2025.06
mkdir -p $EESSI_USER_INSTALL

module load EESSI-extend
eb --show-config
eb <easyconfig>.eb --robot
#+end_example

Chapter 10's =--show-config= earns its place again. Run it and read
=installpath=: it comes back qualified by microarchitecture, something
like =.../software/linux/x86_64/amd/zen5=.

Stop and look at that path. It is [[file:06-what-installed-means.org][chapter 6]]'s per-architecture tree, and
here the architecture is *in the path* rather than hidden behind a
symlink. Same arrangement, made visible. A binary built here is for one
microarchitecture and says so.

There are four prefix variables, and they differ in who can read the
result:

| Variable | What it means |
|---+---|
| =EESSI_USER_INSTALL= | private to the operator |
| =EESSI_PROJECT_INSTALL= | shared with a group |
| =EESSI_SITE_INSTALL= | site-wide, on top of EESSI |
| =EESSI_CVMFS_INSTALL= | into the distributed repository itself |

Set the prefix *before* loading the module. =EESSI-extend= reads
these at load time; setting them afterwards changes nothing.

=EESSI_CVMFS_INSTALL= and =EESSI_SITE_INSTALL= are exclusive of the
others. =EESSI_USER_INSTALL= and =EESSI_PROJECT_INSTALL= may be set
together: both prefixes appear on =MODULEPATH=, and new installs go
to the user prefix.

#+ATTR_EB: :id EB-EESSI-1 :title Every dependency says SKIPPED
#+begin_exercise
You have set one prefix variable, loaded =EESSI-extend= on the
=2025.06= tree, and run a plan for an easyconfig on =foss-2026.1=.
Every dependency comes back =[SKIPPED]=, and the run opens by fetching
a couple of hundred megabytes of GCC.

1. What has happened?
2. You could let it run. Give two reasons not to.
3. What is the honest thing to report, and to whom?

#+begin_solution
The compatibility layer for EESSI 2025.06 does not carry
=foss-2026.1=. (It does carry =foss-2025b=; that pin would not have
produced this plan.) Nothing above the compiler exists to be reused, so
the plan is to build the generation itself, starting with the compiler.

Two reasons not to. It duplicates work the EESSI build bots do centrally
for every supported CPU target, where yours would cover one. And what you
end up with is a whole generation inside a user prefix that nobody else
can use and that you now maintain.

The honest report is a generation gap: this recipe needs =foss-2026.1=,
this EESSI version's layer stops short of it, so the ceiling here is a
build on an ordinary target rather than an EESSI-verified one. That goes
to whoever asked for the software, and the software-layer entry waits for
an EESSI version whose layer carries the generation.
#+end_solution
#+end_exercise

* When the filesystem client is the problem

The symptoms lie, in a specific way.

A host's client can report healthy while being unusable. The probe says
fine and the server answers a plain HTTP request in milliseconds. Every
directory listing into a nested path then blocks forever, and poisons
the shell it ran in.

Two ways out, in order of preference.

If the account has polkit rights on the host, which an ordinary user often
does, restarting the mount clears the stuck readers. Do it from a
terminal that did *not* run the hanging command, because that shell is
itself stuck behind its own filesystem operation.

If the account does not, use a container. It mounts the distributed filesystem
itself, needs only unprivileged user namespaces, and does not care what
state the host client is in:

#+begin_example
git clone --depth 1 https://github.com/EESSI/software-layer-scripts.git
export APPTAINER_CACHEDIR=$PWD/storage/apptainer-cache
./software-layer-scripts/eessi_container.sh \
  --mode exec --access ro --storage $PWD/storage \
  --extra-bind-paths "$PWD/ecs:/ecs:ro" \
  -- /bin/bash /ecs/run-extend.sh
#+end_example

Four details that each cost an attempt:

- the script lives in =software-layer-scripts=. It moved, and
  =software-layer= no longer carries it.
- =--mode run= warns and behaves as =exec=. Pass =exec=.
- the script that is run must be inside a bound path. One that resolves
  outside the bind mount fails as though the file were absent.
- set =APPTAINER_CACHEDIR=. With the older =SINGULARITY_= name also
  set, the older one wins and the newer is dropped with no message.

Diagnosing the host client further rarely pays. On one host, root-catalog
fetches succeeded while nested traversal stalled. A second server,
disabled timeouts and a wiped cache each changed nothing, and a
container on the same host and network traversed everything
instantly.

* Building by hand on top of it

Sometimes something has to be built without EasyBuild. Load the
toolchain's =buildenv= module rather than improvising:

#+begin_example
module load buildenv/default-foss-2025b
module load <dependency modules>
make
readelf -d <binary>
ldd <binary>
#+end_example

=buildenv= sets =$CC= and =$CFLAGS= the way EasyBuild would. It also
installs the wrappers that inject RPATH. The two commands after =make=
are chapter 6's third check, run by hand. Confirm the binary records a
runtime path, then confirm nothing resolves outside the stack.

* Contributing back

An installation in a local prefix helps that operator. Getting it into EESSI proper
is a different job, and the order matters. The six steps below are the
postcard. [[file:30-easystack-files.org][Chapter 30]] is the YAML. [[file:31-the-eessi-bot.org][Chapter
31]] is the comment that starts the build and the ingest that makes a
module. [[file:32-host-injections.org][Chapter 32]] is the site tree that
never goes into =software.eessi.io=.

1. Get the easyconfig into EasyBuild, or open a pull request for it.
2. Build it in the EESSI build environment with =EESSI-extend=.
3. Add an entry to the easystack file for that EESSI version and
   toolchain generation.
4. Open a pull request against the software layer, targeting =main=.
5. A builder posts one =bot: build for:arch=...= per supported CPU
   target.
6. On green, =bot:deploy= uploads the tarballs; a Stratum-0 ingest
   is what publishes them.

Two conditions before the work starts.

The easyconfig comes first. A software-layer entry references an
easyconfig rather than restating one. So deployment waits on the
EasyBuild pull request being merged, even though the two can be open
at once.

And a green build on your host is not the claim. The bot builds
x86-64 down to generic and up through Zen and Sapphire Rapids, plus
aarch64 from generic through Neoverse and Grace. Software that works on
your microarchitecture and not the others is not ready, however green it
looks locally. That is the same distinction as chapter 6's, with a
larger set of trees.

* The three that bite

Everything else in this chapter is procedure. These three cost real
time, and in this order.

*List before descending.* A version directory can be an unpopulated
placeholder. One speculative listing into it wedges the filesystem
client for every user on the host. Confirm an =init/= exists first.

*Check the generation before planning.* The compatibility layer lags
the newest toolchain generation. A gap is a finding to report, not
something to bootstrap a compiler around.

*One prefix variable, set before the module load.* =EESSI-extend=
reads it at load time. A second one, or a late one, produces a failure
that looks like the module ignoring the request.

After that, two things to keep in view. =installpath= comes back
microarchitecture-qualified, which is chapter 6's per-architecture tree
with the architecture visible in the path. And the all-CPU-target claim
belongs to the bot rather than to your host.
