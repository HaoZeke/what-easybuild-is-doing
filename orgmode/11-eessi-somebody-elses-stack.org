* The stack is a filesystem

#+begin_example
ls /cvmfs/software.eessi.io/versions/
#+end_example
These are versions of a complete scientific software stack: compilers, MPI, the usual suspects, tuned per microarchitecture, delivered on a filesystem that arrived over HTTP.
EESSI is not installed.
It is mounted, or the session runs on a machine where it has already been mounted.
Select one and initialise it.
#+begin_example
source /cvmfs/software.eessi.io/versions/2025.06/init/lmod/bash
#+end_example
=init/lmod/bash= configures Lmod for the session.
=init/bash= is the irreversible client init; do not source it to
"just get Lmod".
A compatibility layer, a module tree, and a collection of toolchains are created without requiring an install step or any maintainer approval.
Two warnings must be placed here before any other content.
Each consumes actual time.
The first warning concerns the =ls= command.
List the versions directory and verify that a version is valid before using it.
#+begin_example
ls /cvmfs/software.eessi.io/versions/<ver>/init/lmod/bash
#+end_example
A listed version may be an empty placeholder lacking any =init/=.
Speculatively descending into such a placeholder can wedge the filesystem client for all host users.
The lookup neither resolves nor raises an error, and readers accumulate in an uninterruptible state beyond any timeout reach.
List first.
Confirm.
Then use.
The second concerns the generation question, which determines whether the remainder of this page applies.
* Check the generation before planning anything
The compatibility layer is behind the newest EasyBuild toolchain generation.
A version of EESSI includes a specific set of top‑level toolchains.
An easyconfig names a particular generation.
These two facts must agree.
If they do not agree, EESSI reports the mismatch.
An opt‑in is available.
#+begin_example
export EESSI_SITE_TOP_LEVEL_TOOLCHAINS_2025_06='[{"name": "GCCcore", "version": "15.2.0"}]'
#+end_example
A setting triggers EasyBuild *plan* the build.
Read the plan prior to script execution.
When the generation is absent from the compatibility layer, every dependency is skipped.
The run then begins by bootstrapping the compiler itself and downloading a couple of hundred megabytes of GCC.
Avoid this.
Bootstrapping an entire generation into a user prefix duplicates what EESSI's own build bots do centrally.
It also creates a long detour to a stack that cannot be shared.
A generation gap means not yet on this EESSI version.
This is a finding rather than a failure.
* Installing on top, with EESSI-extend
EESSI supplies a module that configures EasyBuild for stack installation.
Build bots use the same module.
This path matches the bot's actions.
#+begin_example
source /cvmfs/software.eessi.io/versions/2025.06/init/lmod/bash

export EESSI_USER_INSTALL=$HOME/eessi/2025.06
mkdir -p $EESSI_USER_INSTALL

module load EESSI-extend
eb --show-config
eb <easyconfig>.eb --robot
#+end_example
Build your own without asking anyone.
=--show-config= earns its place again.
Run it and read =installpath=.
It returns a path qualified by microarchitecture, for example =.../software/linux/x86_64/amd/zen5=.
Stop and look at that path.
It is [[file:06-what-installed-means.org][What "installed" means]]'s per-architecture tree.
The architecture appears *in the path* instead of being hidden behind a symlink.
Same arrangement, made visible.
A binary built here is for one microarchitecture and says so.
Four prefix variables exist.
They differ in who can read the result.

| Variable | What it means |
|---+---|
| =EESSI_USER_INSTALL= | private to the operator |
| =EESSI_PROJECT_INSTALL= | shared with a group |
| =EESSI_SITE_INSTALL= | site-wide, on top of EESSI |
| =EESSI_CVMFS_INSTALL= | into the distributed repository itself |

Set the prefix *before* loading the module.
=EESSI-extend= reads these at load time.
Setting them afterwards changes nothing.
=EESSI_CVMFS_INSTALL= and =EESSI_SITE_INSTALL= are exclusive of the others.
=EESSI_USER_INSTALL= and =EESSI_PROJECT_INSTALL= may be set together.
Both prefixes appear on =MODULEPATH=.
New installs go to the user prefix.
#+ATTR_EB: :id EB-EESSI-1 :title Every dependency says SKIPPED
#+begin_exercise
You have set one prefix variable, loaded =EESSI-extend= on the
=2025.06= tree, and run a plan for an easyconfig on =foss-2026.1=.
Every dependency comes back =[SKIPPED]=, and the run opens by fetching
a couple of hundred megabytes of GCC.

1. What has happened?
2. You could let it run. Give two reasons not to.
3. What is the honest thing to report, and to whom?

#+begin_solution
The compatibility layer for EESSI 2025.06 does not carry
=foss-2026.1=. (It does carry =foss-2025b=; that pin would not have
produced this plan.) Nothing above the compiler exists to be reused, so
the plan is to build the generation itself, starting with the compiler.

Two reasons not to. It duplicates work the EESSI build bots do centrally
for every supported CPU target, where yours would cover one. And what you
end up with is a whole generation inside a user prefix that nobody else
can use and that you now maintain.

The honest report is a generation gap: this recipe needs =foss-2026.1=,
this EESSI version's layer stops short of it, so the ceiling here is a
build on an ordinary target rather than an EESSI-verified one. That goes
to whoever asked for the software, and the software-layer entry waits for
an EESSI version whose layer carries the generation.
#+end_solution
#+end_exercise

* When the filesystem client is the problem
Symptoms manifest in a specific way.
A host client may report healthy yet be unusable.
The probe reports fine and the server answers a plain HTTP request within milliseconds.
Every directory listing into a nested path then blocks forever and poisons the shell that ran it.
Two solutions exist, ordered by preference.
If the account has polkit rights on the host, which an ordinary user often does, restarting the mount clears the stuck readers.
The operation should be performed from a terminal that did not run the hanging command.
If the account lacks polkit rights, a container can be used.
The container mounts the distributed filesystem itself, requires only unprivileged user namespaces, and is independent of the host client state.
#+begin_example
git clone --depth 1 https://github.com/EESSI/software-layer-scripts.git
export APPTAINER_CACHEDIR=$PWD/storage/apptainer-cache
./software-layer-scripts/eessi_container.sh \
 --mode exec --access ro --storage $PWD/storage \
 --extra-bind-paths "$PWD/ecs:/ecs:ro" \
 -- /bin/bash /ecs/run-extend.sh
#+end_example
Each of four details costs an attempt.
The script lives in =software-layer-scripts=.
It was moved.
=software-layer= no longer carries it.
=--mode run= warns.
=--mode run= behaves as =exec=.
Pass =exec=.
The script that is run must be inside a bound path.
A script that resolves outside the bind mount fails as though the file were absent.
Set =APPTAINER_CACHEDIR=.
With the older =SINGULARITY_= name also set, the older one wins.
The newer name is dropped with no message.
Diagnosing the host client further rarely pays.
On one host, root-catalog fetches succeeded.
Nested traversal stalled on that host.
A second server disabled timeouts.
A second server wiped the cache.
Neither change affected the outcome.
A container on the same host and network traversed everything instantly.
* Building by hand on top of it
Building without EasyBuild may be required.
Load the =buildenv= module of the toolchain instead of improvising.
#+begin_example
module load buildenv/default-foss-2025b
module load <dependency modules>
make
readelf -d <binary>
ldd <binary>
#+end_example
=buildenv= configures =$CC= and =$CFLAGS= in the same way as EasyBuild.
Wrappers that inject RPATH are installed.
The two commands after =make= constitute the third check of What "installed" means, executed manually.
The binary records a runtime path.
Nothing resolves outside the stack.
* Contributing back
Installing in a local prefix assists the operator.
Moving it into EESSI proper requires a separate task.
The order is important.
These six steps constitute the postcard.
[[file:30-easystack-files.org][An easystack is the list the bot will build]] is the YAML.
[[file:31-the-eessi-bot.org][The bot is three processes and a comment]] is the comment that starts the build and the ingest that creates a module.
[[file:32-host-injections.org][A site stack next to EESSI, not inside it]] is the site tree that never goes into =software.eessi.io=.
Place the easyconfig into EasyBuild, or open a pull request for it.
Build it in the EESSI build environment using =EESSI-extend=.
Add an entry to the easystack file for that EESSI version and toolchain generation.
Open a pull request against the software layer, targeting =main=.
A builder posts one ~bot: build for:arch=...~ per supported CPU target.
When green, =bot:deploy= uploads the tarballs.
A Stratum-0 ingest publishes them.
Two conditions apply before work starts.
The easyconfig must come first.
A software-layer entry references an easyconfig instead of restating one.
Deployment waits for the EasyBuild pull request to be merged, even though both can be open simultaneously.
A green build on the host does not constitute the claim.
The bot builds x86-64 from generic up through Zen and Sapphire Rapids, and builds aarch64 from generic through Neoverse and Grace.
Software that works only on the local microarchitecture is not ready, regardless of local green status.
That matches the distinction of What "installed" means, with a larger set of trees.
* The three that bite
The rest of this page outlines procedures.
The three steps require real time.
The steps must be performed in the given order.
*List before descending.* A version directory may act as an unpopulated placeholder.
Speculative listing into such a directory wedges the filesystem client for every user on the host.
Confirm that an =init/= exists before proceeding.
*Check the generation before planning.* The compatibility layer lags behind the newest toolchain generation.
Report a gap as a finding.
Do not use it to bootstrap a compiler.
*One prefix variable, set before the module load.* The =EESSI-extend= reads it at load time.
A second or late variable causes a failure that appears as the module ignoring the request.
After that, keep two aspects in view.
The =installpath= returns a microarchitecture‑qualified path.
The path corresponds to What "installed" means's per‑architecture tree with the architecture visible in the path.
The all‑CPU‑target claim belongs to the bot.
It does not belong to the host.
