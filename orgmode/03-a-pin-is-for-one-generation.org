#+TITLE: A pin is for one generation
#+OPTIONS: toc:nil num:nil

This is the chapter I would keep if I had to throw the rest away.

Here is a dependency list:

#+begin_src easyconfig :widget parse :hydrate load
name = 'example'
version = '1.0'
toolchain = {'name': 'foss', 'version': '2025a'}

dependencies = [
    ('HDF5', '1.14.6'),
    ('netCDF', '4.9.3'),
]
#+end_src

Almost everyone reads =('HDF5', '1.14.6')= as "needs HDF5, at least
1.14.6". Every other packaging system they have used works that way.
=install_requires= in Python takes =>=1.14.6=. Cargo takes =1.14.6=
and means "compatible with". Conda takes =>=1.14.6,<2=.

EasyBuild has no such syntax: no operator, no range, no caret, no
tilde. A dependency is a name and a version, and the version is the
version. That exact module, or the build does not resolve.

You can check that rather than take it from me. =_parse_dependency= in
=easybuild/framework/easyconfig/easyconfig.py= says what a dependency is,
in its docstring:

#+begin_quote
dep can be a dict, a tuple or a list. if it is a tuple or a list the
attributes are expected to be in the following order: ('name',
'version', 'versionsuffix', 'toolchain'). of these attributes, 'name'
and 'version' are mandatory
#+end_quote

Four positional attributes, two of them required, and the dict it
produces carries a single =version= string. A comparator has nowhere to
go. The version can be *templated*, so the literal text in the file may
read =%(pyshortver)s= rather than a number. A template still resolves to
one exact version. Nothing in the format expresses a set.

* Why that is fine, and then why it is not

Within one generation that exactness is the point. A software stack
built by one organisation for one year should be *reproducible*, and a
range is the enemy of reproducibility. If =foss-2025a= provides HDF5
1.14.6, then every package on =foss-2025a= that wants HDF5 gets 1.14.6,
and the stack has one HDF5 rather than four. A resolver with ranges
would give you four.

So the exactness earns its place. The trouble starts the moment the
easyconfig outlives the generation it was written for.

* The thing that breaks

You have an easyconfig that works on =foss-2025a=. You want it on
=foss-2024a=, maybe because a user is stuck on the older stack, maybe
because you are backfilling. The easyconfig says HDF5 1.14.6, and
=foss-2024a= carried HDF5 1.14.3.

The build fails. Nothing called HDF5 1.14.6 exists in that generation,
and nothing ever will: generations do not gain new versions
retroactively.

Now look at what the easyconfig told you. It said "1.14.6". Did
the software require 1.14.6? Almost certainly not. It required
something, some feature that landed in some earlier version. 1.14.6 is
*what that generation happened to contain* when someone wrote the
easyconfig down. The number records a build environment. It says
nothing about what the package itself needs.

That is the whole insight, stated flatly:

#+begin_quote
A dependency version in an easyconfig is an exact pin for the
generation the easyconfig was written against. Carried across generations,
it states a requirement the software never made.
#+end_quote

* This is why retargeting is not a text edit

The first move that comes to mind, when you want an easyconfig on another
generation, is to open it and change =2025a= to =2024a=. Then the build
fails on HDF5, so you change 1.14.6 to 1.14.3. Then it fails on netCDF,
so you look up what =foss-2024a= provides, and change that. Twenty
minutes later you have an easyconfig that builds and no record of
which of those numbers were requirements and which were incidental.

The right shape is different. Treat the old easyconfig's versions as
*floors*: evidence about what the package was once seen to work with.
The target generation's available modules are the *candidates*.
Something then has to choose a set of candidates that satisfies the
floors and stays internally consistent. That is a solver's job, not a
text editor's.

And the floors themselves only hold within one generation, for the
reason above. Moving generation, they have to be dropped, and something
has to decide what the target generation offers instead.

* Where the real lower bound lives

Dropping the floor is a fallback. The answer lies elsewhere: if you
need the minimum, it is written down, just not in the easyconfig.

- The project's own build system says it. =find_package(HDF5 1.10
  REQUIRED)= in CMake is a real lower bound, stated by the people who
  wrote the software. So is a =requires-python= or a dependency
  specifier in =pyproject.toml=.
- Other packaging ecosystems record it, because their formats can. A
  conda-forge recipe or a Spack =package.py= keeps the constraint *and*
  the condition it applies under, because both formats have somewhere
  to put it.

Either of those is evidence. The following is not: "the older
generation carried an older version, and the build passed". That tells
you a version was sufficient on one machine on one day. Worth having,
and a different claim.

If you retarget an easyconfig and you care whether it is right, say in the
commit message which of the two your bound came from.

* A worked case, because the abstraction is slippery

Take the code-server easyconfig from [[file:01-an-easyconfig-is-python.org][chapter 1]]. It has no dependencies at
all, which makes it a poor example of pinning. It is a perfect example
of the *other* half of this problem: what a generation contains.

code-server 4.130.0 is a real, released, upstream easyconfig.
EasyBuild's own 5.2.0 and 5.2.1 releases carried these versions:

#+begin_example
4.9.1  4.16.1  4.21.1  4.22.1  4.89.1  4.90.2  4.93.1  4.97.2
4.100.2  4.103.2  4.104.0  4.104.1  4.104.2  4.104.3  4.105.1
#+end_example

The list stops at 4.105.1. So a site running EasyBuild 5.2 can have a
perfectly valid easyconfig for 4.130.0 in front of it and still not
build it. "The easyconfig exists" and "the easyconfig exists in the
release you are running" are different statements, and both held at
once here.

The same distinction applies to pinning. "HDF5 1.14.6 exists" is
not "HDF5 1.14.6 exists in =foss-2024a=", and an easyconfig cannot tell
the difference because it names a version and not a generation.

* One thing to do differently

Next time you move an easyconfig to another generation, write down in
the commit message where each changed version came from. The project's
own build system, another packaging format that can express a
condition, or the shelf.

The first two are bounds. The third is a build environment you happened
to meet. The next person to move this file will thank you for saying
which is which.
