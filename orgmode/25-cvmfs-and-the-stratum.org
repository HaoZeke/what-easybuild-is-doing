[[file:11-eessi-somebody-elses-stack.org][Chapter 11]] used a software
stack from =/cvmfs= without saying what =/cvmfs= is.

CernVM-FS is a read-only filesystem delivered over plain HTTP, which
means the whole thing can be read with a shell. Every command in this
chapter runs on an ordinary machine with no CernVM-FS client, no mount,
no privileges and no account: the public EESSI repository answers plain
GET requests. So this chapter verifies rather than describes, and every
number in it came back from the network on 2026-09-10.

Set this once and the rest follows:

#+begin_example
base=http://s1eessieu1-cvmfs.openhtc.io/cvmfs/software.eessi.io
#+end_example

Thirteen fields, one letter each, then a separator, a 40-character
certificate fingerprint and 256 bytes of signature: 603 bytes in total
for a repository holding three generations of a software stack. Four
fields are the ones you will use.

=C= is the content hash of the root file catalog. =B= is that catalog's
size, 26624 bytes. =S= is the revision, 23927, which is how many times
this repository has been published. =D= is the time to live of the root
catalog in seconds: 240, four minutes, which is the interval after which
a client will look for a newer revision.

=R= is =d41d8cd98f00b204e9800998ecf8427e=, which is the MD5 of the empty
string, because it is the MD5 of the repository's root path and the root
path is empty. =T= is a Unix timestamp, here 2026-09-09 08:41:32 UTC.
=X= is the hash of the certificate that signed this, and =H=, =M= and =Y=
are hashes of the tag history, the repository metadata and the reflog
checksum.

The same request against a different Stratum 1 comes back byte for byte
identical:

#+begin_src ebtranscript :source "curl against two EESSI Stratum 1 endpoints, 2026-09-10" :caption "Two replicas, one answer"
$ curl -sS http://aws-eu-central-s1.eessi.science/cvmfs/software.eessi.io/.cvmfspublished \
>   | head -2
C7ca4fb6b5db9c1432243b47e306e46327cdeda19
B26624
#+end_src

Which is what replication means here: a Stratum 1 is a mirror of
immutable objects plus a copy of the signed manifest, not an independent
service with its own state.

* Content addressing, checked rather than believed

#+ATTR_EB: :title Two numbers, before you look
#+begin_predict
The manifest above says the root catalog hashes to =7ca4fb...= and
=B26624=. You are about to fetch that object over HTTP and hash it.

Predict two things: what =sha1sum= of the downloaded bytes will be, and
how many bytes the download will be.

#+begin_reveal
=sha1sum= returns =7ca4fb6b5db9c1432243b47e306e46327cdeda19=: exactly the
name it was requested under. That is what content addressing means, and it
is checkable without trusting the server that sent it.

The download is 5511 bytes, not 26624. The hash covers the *compressed*
form, and =B= in the manifest is the uncompressed size. Decompressing the
5511 bytes gives exactly 26624, and what comes out is a SQLite database.
#+end_reveal
#+end_predict


The manifest says the root catalog is =7ca4fb...=. Objects live under
=data/=, split into 256 directories by the first two hex digits of their
own hash:

#+begin_src ebtranscript :source "curl and python3 against the EESSI Stratum 1, local workstation, 2026-09-10" :caption "Fetch by hash, then check the hash"
$ h=7ca4fb6b5db9c1432243b47e306e46327cdeda19
$ curl -sS -o cat.obj $base/data/${h:0:2}/${h:2}C
$ ls -l cat.obj
-rw-r--r-- 1 rgoswami rgoswami 5511 Sep 10 07:28 cat.obj

$ sha1sum cat.obj
7ca4fb6b5db9c1432243b47e306e46327cdeda19  cat.obj

$ python3 -c "import zlib; d=open('cat.obj','rb').read();
> u=zlib.decompress(d); open('cat.db','wb').write(u);
> print(len(u), 'bytes uncompressed')"
26624 bytes uncompressed

$ file cat.db
cat.db: SQLite 3.x database, page size 1024, ... database pages 26, ...
#+end_src

Four facts fall out of those five commands, and each of them is a claim
the documentation makes and this checks.

*The name is the hash.* =sha1sum= of the bytes that came back equals the
name they were requested under. Nothing in the transport had to be
trusted for that to be checkable.

*The hash covers the compressed form.* The documentation says "The
cryptographic content hash refers to the zlib-compressed version of the
file", and the numbers agree: 5511 bytes stored, hashing to the object
name; 26624 bytes after decompression.

*=B= in the manifest is the uncompressed size.* 26624, exactly what
=zlib.decompress= produced.

*A catalog is a SQLite database.* Not a format to reverse-engineer; a
file you can open.

#+ATTR_EB: :id cvmfs-object-suffix :title The trailing C, and where it is not written down :kind discrepancy
#+begin_detail
The object was fetched from =data/7c/a4fb...cdeda19C=, with a =C=
appended. Without it:

#+begin_example
$ curl -sS -o obj.bin -w 'HTTP %{http_code}\n' $base/data/7c/a4fb...cdeda19
HTTP 404

$ curl -sS -o obj.bin -w 'HTTP %{http_code}\n' $base/data/7c/a4fb...cdeda19C
HTTP 200
#+end_example

CernVM-FS's server infrastructure appendix documents the =00..ff= split
and the content-addressed naming, and does not document this suffix. It
was established here by trying both, against the live repository: 404 and
200. Treat the suffix as a fact about the deployed format rather than a
documented interface, and expect regular file objects to have no suffix,
which is what the =.cvmfsdirtab= fetch later in this chapter relies on.
#+end_detail

* Inside the catalog

#+begin_src ebtranscript :source "sqlite3 on the decompressed root catalog of software.eessi.io, revision 23927, 2026-09-10" :caption "What a file catalog actually holds"
$ sqlite3 cat.db '.tables'
bind_mountpoints  catalog  chunks  nested_catalogs  properties  statistics

$ sqlite3 cat.db 'pragma table_info(catalog)' | cut -d'|' -f2 | tr '\n' ' '
md5path_1 md5path_2 parent_1 parent_2 hardlinks hash size mode mtime
flags name symlink uid gid xattr mtimens

$ sqlite3 cat.db 'select key, value from properties order by key'
TTL|240
last_modified|1788943289

revision|23927
schema|2.5
schema_revision|8
#+end_src

=md5path_1= and =md5path_2= are the two halves of an MD5: paths are not
stored, their hashes are. "In order to save space we do not store
absolute paths. Instead, we store MD5 hash values of the absolute path
names." A lookup is therefore a hash and an index probe, at any depth,
and the price is that a catalog cannot be listed by prefix.

=previous_revision= is a hash, which makes the repository a chain: every
published revision names the one before it.

The =flags= column encodes what an entry is, and the live histogram is
small enough to read whole:

#+begin_src ebtranscript :source "sqlite3 on the same root catalog, 2026-09-10" :caption "Every entry in the root catalog, by kind"
$ sqlite3 cat.db 'select flags, count(*) from catalog group by flags order by 2 desc'
12|33
1|16
4|3
3|3
#+end_src

Sixteen directories (flag 1), three regular files (flag 4), thirty-three
symlinks (12, which is 4 for a file and 8 for a symlink), and three
entries with flag 3.

Three, not two. The documentation says a nested-catalog transition
directory "appears as empty directory in the parent catalog with flags set
to 2", and in the live catalog those entries carry 3, because bit 1,
directory, is also set. The =statistics= table settles it arithmetically
rather than by argument: in the =/versions/2025.06= catalog, =self_nested=
is 501 and exactly 501 entries carry flags 3, while =self_dir= is 755,
which is 501 plus the 253 entries with flags 1 plus the single entry with
flags 33, the nested catalog's own root directory. Transition points are
counted as directories, because they are directories.

The three in the root catalog are exactly the three the =nested_catalogs=
table names:

#+begin_src ebtranscript :source "sqlite3 on the same root catalog, 2026-09-10" :caption "Where the repository is cut"
$ sqlite3 cat.db 'select path, sha1, size from nested_catalogs order by path'
/versions/2023.06|e466e9788ded...|91136
/versions/2025.06|36562d2b1128...|247808
/versions/2026.06|dc9037b9aa27...|174080

$ sqlite3 cat.db "select name from catalog where flags=3"
2023.06
2025.06
2026.06
#+end_src

So the root catalog of the entire EESSI software stack is 26 kilobytes
and knows almost nothing. It knows the top-level layout, and for each
EESSI version it has a hash and a promise. Ask for anything under
=/versions/2025.06= and the client fetches that catalog first, verifies
it the same way, and continues. There is no limit on the nesting, and a
client that never enters a subtree never downloads its metadata.

Which is also why signing the manifest is enough: the root catalog's hash
is in the signed manifest, each nested catalog's hash is in its parent,
and each file's hash is in the catalog that lists it. A Merkle tree, with
one signature at the top.

Fifty-one million files and 6.8 terabytes, accounted for by a 26-kilobyte
database that itself lists twenty-five entries. Forty thousand nested
catalogs is what makes that work: a client mounting the repository fetches
this one file, and the metadata for anything it does not open costs it
nothing.

One level down, =/versions/2025.06= is a 247-kilobyte catalog with 891
entries, of which 501 are transition points into further catalogs, and its
own subtree accounts for 3.68 terabytes. Its =properties= table carries
=root_prefix= =/versions/2025.06= and revision 9291, and *no* TTL row:
the time to live lives in the root catalog only.

Deeper again, for one CPU target, the split is visible in the shape of the
two catalogs: =x86_64/amd/zen4/modules= has 3241 entries and no nested
catalogs, because a =module avail= should not touch a thousand databases;
=x86_64/amd/zen4/software= has 1609 entries and 1078 nested catalogs, one
per installation directory, accounting for 114.7 gigabytes. So listing the
modules is cheap and opening one package's files is cheap, which is the
pair of properties a software stack needs.
#+end_detail

#+ATTR_EB: :id EB-CVMFS-2 :title Verify a repository yourself
#+begin_exercise
Do this one rather than reading it. You need =curl=, =python3= and
=sqlite3=, and no privileges.

1. Fetch =.cvmfspublished= from a public Stratum 1 and read off =C=, =B=,
   =S= and =D=.
2. Fetch the root catalog object by its hash and check =sha1sum= against
   the name you requested.
3. Decompress it and compare the byte count with =B=.
4. Open it with =sqlite3= and count the entries by =flags=.
5. Then answer: what would you have to compromise to serve a reader a
   modified file without them noticing?

#+begin_solution
Steps 1 to 4 are the transcripts in this chapter, against whichever
repository you pick; the numbers will differ and the relationships will
not. If =sha1sum= disagrees with the object name, you have found either a
corrupted mirror or a much more interesting problem.

Step 5 is the point of the exercise. To change one file you need a catalog
that names its new hash; to change a catalog you need its parent to name
*that* new hash, recursively, up to the root; and the root catalog's hash
is in the signed manifest. So you need the repository's private key, and
then also to defeat the whitelist, which is signed by a different key
whose public part reached the client out of band.

What you do *not* need to compromise: any Stratum 1, any proxy, or the
network. Those carry immutable objects that the client checks for itself,
which is why the transport can be plain HTTP.

The one place the chain stops is the local cache, which the client trusts
once an object is in it.
#+end_solution
#+end_exercise

* Two keys

The signature at the bottom of the manifest is made with the *repository*
key, which lives on the publisher. The list of certificates allowed to
sign is =.cvmfswhitelist=, and that is signed with a different key:

#+begin_quote
The whitelist is signed with a different RSA key, the *repository master
key*. Only the public part of this master key needs to be distributed to
clients.
#+end_quote

The master public key cannot arrive through the repository it
authenticates: "The public key used to ultimately verify a repository's
signature needs to be distributed to clients through a channel different
from CernVM-FS content distribution." For EESSI that channel is a
package, =cvmfs-config-eessi=, which installs
=/etc/cvmfs/keys/eessi.io/eessi.io.pub=.

Whitelists expire. "Signatures are only good for 30 days by default, so
=cvmfs_server resign= must be run again before they expire", and seven
days rather than thirty when the master key sits on a hardware token. A
compromised repository key is handled with a blacklist that "has
precedence over the white-list", and with one limit stated plainly
upstream:

#+begin_quote
Blacklisted fingerprints prevent clients from loading future repository
publications by a corresponding compromised repository key, but they do
not prevent mounting a repository revision that had previously been
mounted on a client, because the catalog for that revision is already in
the cache.
#+end_quote

* One writer

New content enters at exactly one place, the *Stratum 0*, on a machine
called the release manager or publisher. The publisher mounts the
repository read-only and puts a union filesystem over it, so a change
goes to a scratch area rather than into the repository.
=cvmfs_server transaction= opens that, =publish= converts what changed
into the storage format above, =abort= discards it. Upstream's phrase for
the property that matters is three words: "Publishing is an atomic
operation."

Everything a client sees, therefore, is a published revision: the =S=
field, with a =previous_revision= hash behind it, and clients that refuse
to go backwards. "Once a particular revision of a file system is stored
in a client's local cache, the client will not apply an older revision
anymore."

* Getting it to a thousand machines

A Stratum 1 is "a standard web server that uses the CernVM-FS server
toolkit to create and maintain a mirror of a CernVM-FS repository served
by a Stratum 0 server", registered with =cvmfs_server add-replica= and
kept current by =cvmfs_server snapshot -a= from cron.

Squid appears twice in a deployment, with different jobs: a reverse proxy
in front of a Stratum 1, and a forward proxy in front of your clients.
The recommended forward-proxy configuration carries one line that decides
how a cluster behaves at the start of a job array:

#+begin_example
collapsed_forwarding on
#+end_example

which "combines multiple simultaneous requests for the same object into a
single request to a Stratum 1 server". Eight hundred nodes starting the
same job ask for the same library in the same second; that line makes it
one request upstream.

* On your machine

The client is a FUSE filesystem mounted by =autofs= on first access, and
unmounted again when nothing has used it for a while. It starts as root
and "drops root privileges and changes the persona to the =cvmfs= user
early in the file system initialization".

#+ATTR_EB: :id cvmfs-caches :title The four caches, and their shipped defaults :kind reference
#+begin_detail
From =/etc/cvmfs/default.conf= as shipped
([[https://github.com/cvmfs/cvmfs/blob/devel/mount/default.conf][cvmfs/cvmfs, devel branch]])
and the client documentation:

| Layer | Setting | Default |
|---+---+---|
| kernel attribute cache | (FUSE) | 1 minute |
| in-memory metadata cache | =CVMFS_MEMCACHE_SIZE= | not stated in the documentation |
| local disk cache | =CVMFS_CACHE_BASE= | =/var/lib/cvmfs= |
| disk cache soft limit | =CVMFS_QUOTA_LIMIT= | =4000= megabytes |
| shared between repositories | =CVMFS_SHARED_CACHE= | =yes= |
| HTTP timeout, with a proxy | =CVMFS_TIMEOUT= | 5 seconds |
| HTTP timeout, direct | =CVMFS_TIMEOUT_DIRECT= | 10 seconds |

Replacement is least-recently-used, and the threshold is not the quota:
"When exceeding the cache quota, files are deleted until the overall cache
size is less than or equal to the cache threshold. The cache threshold is
currently hard-wired to half of the cache quota."

For a single machine the shipped configuration documents
=CVMFS_CLIENT_PROFILE=single= for "laptops or fewer than 5 machines", and
EESSI's own instructions raise the quota to
=CVMFS_QUOTA_LIMIT=10000=.
#+end_detail

A cache miss is then a sequence, and every failure mode belongs to one of
its steps:

1. The path's MD5 is looked up in the catalog. If the path crosses a
   transition point, *that nested catalog is fetched and verified first*.
2. The entry gives a content hash. The object is requested by that hash
   through the proxy chain to a Stratum 1. Concurrent requests for the
   same URL "are collapsed into a single request".
3. It arrives in a temporary file: "Only at the very latest point they
   are renamed into their content-addressable names atomically by
   =rename()=."
4. It is verified against the catalog's hash, then decompressed.
5. Inserting it may evict, down to half the quota.
6. Afterwards =stat()= "can be entirely served from the in-kernel file
   system buffers".

With one bound on all of it, stated upstream: "Once downloaded and stored
in a cache, the CernVM-FS client fully trusts the cache. Data in the
cache can be checked for silent corruption but no integrity re-check
takes place."

* Why it is read-only

Three independent reasons, each sufficient on its own.

*Objects are named by their content.* Changing a file's bytes changes its
name, so there is nowhere to write a modification of a file that is still
that file.

*The signature covers the whole tree.* The signed manifest fixes the root
catalog hash, which fixes every nested catalog and every file hash below
it. A local write breaks the chain that makes the repository verifiable
at all.

*There is no client write path.* Publishing is defined as a server-side
atomic operation through a union filesystem on the release manager
machine.

So the site-specific escape hatch cannot be a write, and it is not. It is
a symlink whose *stored target is a variable reference*, expanded by the
client from its own configuration. Three of them are in the live catalog
above:

#+begin_src ebtranscript :source "sqlite3 on the root catalog of software.eessi.io, revision 23927, 2026-09-10" :caption "Variant symlinks, as stored"
$ sqlite3 cat.db "select name, symlink from catalog where flags=12
>   and symlink like '\$(%'"
host_injections|$(EESSI_HOST_INJECTIONS:-/opt/eessi)
nvidia|$(EESSI_NVIDIA_OVERRIDE_DEFAULT:-/dev/null)
override|$(EESSI_LIB_OVERRIDE_DEFAULT:-/dev/null)
#+end_src

What is signed is that string. A site that points
=EESSI_HOST_INJECTIONS= somewhere else changes what the symlink resolves
to without invalidating a signature, because the repository still
contains exactly the bytes it was signed with. That is the whole trick,
and it is [[file:26-the-same-stack-somewhere-else.org][chapter 26]].

#+ATTR_EB: :id EB-CVMFS-1 :title Six symptoms, six layers
#+begin_exercise
For each, name the layer and the check.

1. A new module appeared on one node twenty minutes ago and is still
   invisible on another.
2. A job's first minute is slow every time, on every node, and fast
   afterwards.
3. =ls /cvmfs/software.eessi.io= works; a file under it gives an
   input/output error.
4. A site with 800 nodes saturates its uplink whenever a job array
   starts.
5. Your laptop's =/var= fills up.
6. A colleague proposes editing a file under =/cvmfs= to test a fix.

#+begin_solution
1. The root catalog's time to live, =D= in the manifest, 240 seconds for
   this repository, plus the kernel attribute cache. The second node has
   not looked for a new revision yet. Check with
   =cvmfs_config stat -v <repo>= and compare the revision each node has
   against =curl $base/.cvmfspublished=.

2. Cache misses, then hits. If it recurs on every node on every run, the
   working set exceeds =CVMFS_QUOTA_LIMIT= and eviction is taking it to
   half the quota between runs, or the cache directory is being cleared.

3. Metadata resolved, content did not: the catalog is cached and an object
   fetch or its verification failed. Check the proxy chain, then fetch the
   object by hand the way this chapter does and compare =sha1sum= against
   the name.

4. Missing forward proxies, or proxies without =collapsed_forwarding on=.
   The requests are identical and simultaneous, which is exactly the case
   that line exists for.

5. =CVMFS_CACHE_BASE= is =/var/lib/cvmfs= by default and the quota is
   4000 MB. Move the cache or lower the quota, and set
   =CVMFS_CLIENT_PROFILE=single= on a single machine.

6. Not possible, and the reason is the format rather than the
   permissions: content-addressed objects, a signed Merkle tree, and no
   client write path. What they want is a variant symlink or a site tree
   under =host_injections=.
#+end_solution

#+begin_keypoints
- A repository is verifiable from one signature because the manifest names
  the root catalog's hash and every catalog names its children's.
- Objects are named by the hash of their compressed bytes, so any client can
  check what it was given without trusting the transport.
- A catalog is a SQLite database keyed by the MD5 of the absolute path, cut
  into nested catalogs that are fetched on first access.
- Two keys: the repository key signs each revision, the master key signs the
  whitelist, and only the master public key has to reach clients out of band.
- A cache miss is a sequence, and the client trusts its cache once the object
  is in it.
#+end_keypoints
