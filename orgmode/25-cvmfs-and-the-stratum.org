The format consists of thirteen fields, each represented by a single letter, followed by a separator, a 40‑character certificate fingerprint, and a 256‑byte signature, totaling 603 bytes for a repository containing three generations of a software stack.
Only four of these fields are used.
=C= is the content hash of the root file catalog.
=B= is the catalog size, 26624 bytes.
=S= is the revision number, 23927.
The revision number is the count of times this repository has been published.
=D= is the time‑to‑live of the root catalog in seconds, 240 (four minutes).
The time‑to‑live is the interval after which a client will look for a newer revision.
=R= is =d41d8cd98f00b204e9800998ecf8427e=.
The value is the MD5 of the empty string.
=T= is a Unix timestamp, 2026-09-09 08:41:32 UTC.
=X= is the hash of the certificate that signed this.
=H=, =M= and =Y= are hashes of the tag history, the repository metadata, and the reflog checksum.

#+ATTR_EB: :title Two numbers, before you look
#+begin_predict
The manifest above says the root catalog hashes to =7ca4fb...= and
=B26624=. The next step is to fetch that object over HTTP and hash it.

Predict two things: what =sha1sum= of the downloaded bytes will be, and
how many bytes the download will be.

#+begin_reveal
=sha1sum= returns =7ca4fb6b5db9c1432243b47e306e46327cdeda19=: exactly the
name it was requested under. That is what content addressing means, and it
is checkable without trusting the server that sent it.

The download is 5511 bytes, not 26624. The hash covers the *compressed*
form, and =B= in the manifest is the uncompressed size. Decompressing the
5511 bytes gives exactly 26624, and what comes out is a SQLite database.
#+end_reveal
#+end_predict
The manifest shows the root catalog =7ca4fb...=.
Objects are stored in =data/=, organized into 256 directories based on the first two hex digits of their hash.

#+ATTR_EB: :id EB-CVMFS-2 :title Verify a repository yourself
#+begin_exercise
Do this one rather than reading it. You need =curl=, =python3= and
=sqlite3=, and no privileges.

1. Fetch =.cvmfspublished= from a public Stratum 1 and read off =C=, =B=,
 =S= and =D=.
2. Fetch the root catalog object by its hash and check =sha1sum= against
 the name you requested.
3. Decompress it and compare the byte count with =B=.
4. Open it with =sqlite3= and count the entries by =flags=.
5. Then answer: what would you have to compromise to serve a reader a
 modified file without them noticing?

#+begin_solution
Steps 1 to 4 are the transcripts in this page, against whichever
repository you pick; the numbers will differ and the relationships will
not. If =sha1sum= disagrees with the object name, you have found either a
corrupted mirror or a much more interesting problem.

Step 5 is why the exercise exists. To change one file you need a catalog
that names its new hash; to change a catalog you need its parent to name
*that* new hash, recursively, up to the root; and the root catalog's hash
is in the signed manifest. So you need the repository's private key, and
then also to defeat the whitelist, which is signed by a different key
whose public part reached the client out of band.

What you do *not* need to compromise: any Stratum 1, any proxy, or the
network. Those carry immutable objects that the client checks for itself,
which is why the transport can be plain HTTP.

The one place the chain stops is the local cache, which the client trusts
once an object is in it.
#+end_solution
#+end_exercise

#+ATTR_EB: :id EB-CVMFS-3 :title Where would that number come from
#+begin_exercise
The root catalog of a repository holding 51.7 million files is 26
kilobytes and lists twenty-five entries.

1. Where does the 51.7 million come from, if the catalog lists
 twenty-five things? Name the table and the column.
2. A client mounts the repository and runs =ls /cvmfs/<repo>=. How many
 catalogs does it fetch, and how many objects?
3. The same client then opens one file inside one package. What does it
 fetch, in order?
4. Somebody proposes flattening the repository into a single catalog for
 simplicity. Using the numbers, say what that would cost the client in
 part 2.

#+begin_solution
1. The =statistics= table, column =subtree_regular=. Every catalog
 carries counters for itself (=self_*=) and for everything below it
 (=subtree_*=), so a 26 kB file can account for a subtree it does not
 list.

2. One catalog, the root, and the objects for whatever =ls= needs, which
 is metadata rather than content: the entries are in the catalog it
 already fetched. The three version directories are transition points,
 and their catalogs are not fetched until something enters them.

3. The version catalog, then the CPU target's =software= catalog, then
 the nested catalog for that installation directory, then the file's
 own object, verified against the hash the catalog gave. Four fetches
 where a flat design would have needed one enormous one.

4. The client would download metadata for 51.7 million files and 8.4
 million directories to answer =ls= on a directory with three entries
 in it. That is the argument for nesting, in one sentence, and it is
 why 40,070 catalogs is a feature rather than an accident.
#+end_solution
#+end_exercise
The manifest's bottom signature uses the *repository* key located on the publisher.
The allowed signing certificates are listed in =.cvmfswhitelist=.
The file is signed with a different key:.
* Two keys
Delivery of the master public key via its repository is not possible.
Distribution of the public key for repository signature verification must use a channel other than CernVM-FS content distribution.
For EESSI, the channel is the package =cvmfs-config-eessi= installing =/etc/cvmfs/keys/eessi.io/eessi.io.pub=.
Whitelists have an expiration.
Signatures are valid for 30 days by default.
=cvmfs_server resign= must be run again before expiration.
When the master key resides on a hardware token, the validity period is seven days instead of thirty.
A compromised repository key is handled with a blacklist that precedes the white‑list.
One limit is stated plainly upstream.
#+begin_quote
The whitelist is signed with a different RSA key, the *repository master
key*. Only the public part of this master key needs to be distributed to
clients.
#+end_quote

#+begin_quote
Blacklisted fingerprints prevent clients from loading future repository
publications by a corresponding compromised repository key, but they do
not prevent mounting a repository revision that had previously been
mounted on a client, because the catalog for that revision is already in
the cache.
#+end_quote
New content is introduced at a single location, the *Stratum 0*.
The machine is called the release manager or publisher.
The release manager mounts the repository read‑only.
The release manager overlays the repository with a union filesystem.
Changes are written to a scratch area instead of the repository.
=cvmfs_server transaction= opens that.
=publish= converts the modifications into the storage format described above.
=abort= discards them.
Upstream describes the relevant property with three words: "Publishing is an atomic operation."
Everything a client observes is a published revision, indicated by the =S= field and a =previous_revision= hash.
A client does not apply an older revision.
When a particular revision of a file system resides in a client's local cache, the client will no longer apply an older revision.
* One writer
Stratum 1 is a standard web server that uses the CernVM-FS server toolkit to create and maintain a mirror of a CernVM-FS repository served by Stratum 0.
It is registered with =cvmfs_server add-replica= and kept current by =cvmfs_server snapshot -a= from cron.
Squid is present twice in a deployment with different jobs: a reverse proxy in front of a Stratum 1 and a forward proxy in front of clients.
The recommended forward-proxy configuration includes one line that decides how a cluster behaves at the start of a job array.

Multiple simultaneous requests for the same object combine into a single request to a Stratum 1 server.
Eight hundred nodes start the same job and request the same library in the same second.
This produces one upstream request.

#+ATTR_EB: :id EB-CVMFS-1 :title Six symptoms, six layers
#+begin_exercise
For each, name the layer and the check.

1. A new module appeared on one node twenty minutes ago and is still
 invisible on another.
2. A job's first minute is slow every time, on every node, and fast
 afterwards.
3. =ls /cvmfs/software.eessi.io= works; a file under it gives an
 input/output error.
4. A site with 800 nodes saturates its uplink whenever a job array
 starts.
5. Your laptop's =/var= fills up.
6. A colleague proposes editing a file under =/cvmfs= to test a fix.

#+begin_solution
1. The root catalog's time to live, =D= in the manifest, 240 seconds for
 this repository, plus the kernel attribute cache. The second node has
 not looked for a new revision yet. Check with
 =cvmfs_config stat -v <repo>= and compare the revision each node has
 against =curl $base/.cvmfspublished=.

2. Cache misses, then hits. If it recurs on every node on every run, the
 working set exceeds =CVMFS_QUOTA_LIMIT= and eviction is taking it to
 half the quota between runs, or the cache directory is being cleared.

3. Metadata resolved, content did not: the catalog is cached and an object
 fetch or its verification failed. Check the proxy chain, then fetch the
 object by hand the way this page does and compare =sha1sum= against
 the name.

4. Missing forward proxies, or proxies without =collapsed_forwarding on=.
 The requests are identical and simultaneous, which is exactly the case
 that line exists for.

5. =CVMFS_CACHE_BASE= is =/var/lib/cvmfs= by default and the quota is
 4000 MB. Move the cache or lower the quota, and set
 =CVMFS_CLIENT_PROFILE=single= on a single machine.

6. Not possible, and the reason is the format rather than the
 permissions: content-addressed objects, a signed Merkle tree, and no
 client write path. What they need is a variant symlink or a site tree
 under =host_injections=.
#+end_solution
#+end_exercise

#+begin_keypoints
- A repository is verifiable from one signature
 the root catalog's hash and every catalog names its children's.
- Objects are named by the hash of their compressed bytes, so any client can
 check what it was given without trusting the transport.
- A catalog is a SQLite database keyed by the MD5 of the absolute path, cut
 into nested catalogs that are fetched on first access.
- Two keys: the repository key signs each revision, the master key signs the
 whitelist, and only the master public key has to reach clients out of band.
- A cache miss is a sequence, and the client trusts its cache once the object
 is in it.
#+end_keypoints
