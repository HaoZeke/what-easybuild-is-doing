#+begin_objectives
1. Get an optimised software stack onto a machine the operator does not administer,
 by three different routes, and say which route fits which machine.
2. Say how EESSI decides which build to give the host it runs on, and
 override that decision.
3. Say what a site adds on top without writing to =/cvmfs=.
#+end_objectives

#+begin_prerequisites
- [[file:25-cvmfs-and-the-stratum.org][Reading a stack off the wire: CernVM-FS]]: this page uses the
 format that one takes apart.
- A machine that can install a package, or a container runtime, or
 neither and read it as reference.
#+end_prerequisites
[[file:25-cvmfs-and-the-stratum.org][Reading a stack off the wire: CernVM-FS]] dissected a repository.
The page uses that repository on machines lacking their own software stack, such as a laptop, a continuous‑integration runner, a cloud instance, and a cluster with externally managed stack.
The tested claim originates from EESSI: "The host OS still provides a couple of things, like drivers for network and GPU, support for shared filesystems like GPFS and Lustre, a resource manager like Slurm, and so on."
All of those components are delivered via HTTP.
* Three layers, and what each one does not do
EESSI has three layers.
The division is the interesting part.

*The filesystem layer* is CernVM-FS.
Reading a stack off the wire: CernVM-FS.
It delivers bytes.
It verifies them.
It knows nothing about software.

*The compatibility layer* is Gentoo Prefix.
It is a set of Gentoo packages installed into a non-standard prefix with Portage.
It provides the libc.
It provides the shell.
It provides the coreutils.
It provides the linker that everything above is built against.
The host distribution stops mattering.

The prefix path is =$EESSI_PREFIX/compat/$EESSI_OS_TYPE/$EESSI_CPU_FAMILY=.
For example =/cvmfs/software.eessi.io/versions/2023.06/compat/linux/x86_64=.

*The software layer* is EasyBuild output.
It includes everything from [[file:02-a-toolchain-is-a-hierarchy.org][A toolchain is a hierarchy]] onwards.
It is built per microarchitecture.
It uses Lmod modulefiles.

The layer boundary that matters for a reader on a laptop is the second one.

A stack built against your distribution's libc would need your distribution.

A stack built against a prefix that travels with it needs a kernel.
It needs not much else.
* Route one: mount it

#+begin_src ebtranscript :source "EESSI native-installation instructions, https://www.eessi.io/docs/getting_access/native_installation/, read 2026-09-10" :caption "The whole of a native install, on any machine you have root on"
# install the CernVM-FS client and the EESSI configuration package
# (cvmfs-config-eessi ships the public key that verifies the repository)

$ sudo bash -c 'echo "CVMFS_CLIENT_PROFILE=single" > /etc/cvmfs/default.local'
$ sudo bash -c 'echo "CVMFS_QUOTA_LIMIT=10000" >> /etc/cvmfs/default.local'
$ sudo cvmfs_config setup
$ ls /cvmfs/software.eessi.io
#+end_src
Two configuration lines affect a single machine.
The setting =CVMFS_CLIENT_PROFILE=single= is shipped for "laptops or fewer than 5 machines".
The setting =CVMFS_CLIENT_PROFILE=single= prevents the client from expecting a site proxy.
Setting =CVMFS_QUOTA_LIMIT=10000= raises the cache from the default 4000 megabytes.
The stack is then one =module use= away.
#+begin_example
module use /cvmfs/software.eessi.io/init/modules
module load EESSI/2023.06
#+end_example
#+begin_example
unset MODULEPATH
source /cvmfs/software.eessi.io/versions/2023.06/init/lmod/bash
#+end_example
* Route two: no root
Two mechanisms exist for two different reasons.
=cvmfsexec= mounts a repository *without* privileges, using user namespaces.
CernVM-FS documents it as the supported way to do that.
The route applies to a shared machine where the account is not an administrator.
The account cannot become an administrator.
A container provides the alternative mechanism.
EESSI publishes the script =eessi_container.sh=, which runs Apptainer or Singularity with the repository mounted inside.
The route is also used by their own build bot, which is worth noticing.
The component that *builds* the stack runs in a container mounting the stack.
* Route three: a runner that exists for ninety seconds
Continuous integration presents a conflict between "install a software stack" and "the job is already over".
EESSI provides a solution.
The runner mounts, resolves required modules, and downloads only the files touched by those modules.
On GitHub Actions the documented route is not a hand‑rolled mount.
It is the published action:.
#+begin_example
- uses: eessi/github-action-eessi@v3
 with:
 eessi_stack_version: '2025.06'
#+end_example
The action relies on =cvmfs-contrib/github-action-cvmfs=.
An operator‑owned runner may still select route one or route two, and the cache reflects that choice.
A fresh runner starts with an empty cache.
The initial job fetches each required object.
* How it chooses what to serve
The component assesses if the stack is fast or merely present.
The initialisation script requests an *ordered* list of targets from a detector.
The script selects the first target that exists on disk.
#+begin_example
all_cpupaths=$(${EESSI_INIT_DIR_PATH}/eessi_archdetect.sh -a cpupath)
IFS=: read -r -a archs <<< "${all_cpupaths}"
for arch in "${archs[@]}"; do
 if [ -d "${EESSI_PREFIX}/software/${EESSI_OS_TYPE}/${arch}" ]; then
 export EESSI_SOFTWARE_SUBDIR="${arch}"
 show_msg "archdetect says ${EESSI_SOFTWARE_SUBDIR}"
 break
 fi
done
#+end_example
=eessi_archdetect.sh -a cpupath= produces a colon‑separated list ordered from the most specific to the most generic.
On an Ice Lake host, EESSI documentation reports the following.
#+begin_example
x86_64/intel/icelake:x86_64/intel/cascadelake:x86_64/intel/skylake_avx512:x86_64/intel/haswell:x86_64/generic
#+end_example
Hosts lacking an exact microarchitecture build receive the best *subset* of the instruction set that has a build, with =x86_64/generic= as the floor.
The fallback policy comprises four lines of shell instead of a resolver.
Two variables are frequently confused.
They are distinct.
=EESSI_CPU_FAMILY= maps directly to the output of =uname -m=.
Examples include =x86_64=, =aarch64=, or =riscv64=.
=EESSI_SOFTWARE_SUBDIR= represents the microarchitecture.
It is set by the loop above.
#+ATTR_EB: :id eessi-overrides :title The override variables, and what they do not check :kind reference
#+begin_detail
All of these must be set *before* initialisation, from
[[https://www.eessi.io/docs/using_eessi/setting_up_environment/][EESSI: setting up your environment]]:

| Variable | Overrides |
|---+---|
| =EESSI_CVMFS_REPO_OVERRIDE= | the repository path |
| =EESSI_VERSION_OVERRIDE= | the version subdirectory |
| =EESSI_SOFTWARE_SUBDIR_OVERRIDE= | the detected microarchitecture |
| =EESSI_ACCELERATOR_TARGET_OVERRIDE= | the detected accelerator |
| =EESSI_ARCHDETECT_OPTIONS_OVERRIDE= | the archdetect options wholesale |
| =EESSI_ACCEL_SOFTWARE_SUBDIR_OVERRIDE= | a different CPU subdir for the accelerator stack |
| =EESSI_BASIC_ENV= | =1= for a minimal initialisation |
| =EESSI_SILENT= | =1= to suppress non-error output |
| =EESSI_USE_ARCHDETECT= | =0= to switch the detector off |
| =EESSI_OVERRIDE_GPU_CHECK= | =1= to load accelerator modules with no driver present |

The documentation notes there is no validation of the values. An
override naming a target that does not exist gives a =MODULEPATH=
pointing at nothing, and the failure appears later as an empty
=module avail=.

Which makes =EESSI_SOFTWARE_SUBDIR_OVERRIDE= the tool for the
measurement in [[file:27-four-things-that-actually-happened.org][Four things that actually happened]]: to see what a different architecture's stack contains, name it,
rather than reasoning about it from the architecture underfoot.
#+end_detail

#+ATTR_EB: :id eessi-archdetect-docs :title Two selectors, and the page that names the wrong one :kind discrepancy
#+begin_detail
[[https://www.eessi.io/docs/software_layer/][The software-layer page]]
says archspec chooses: "We use the *archspec* Python library to
automatically select the best suited part of the software stack for a
particular host, based on its system architecture."

The shipped initialisation defaults say otherwise. In
[[https://github.com/EESSI/software-layer-scripts/blob/main/init/eessi_defaults][init/eessi_defaults]]:

#+begin_example
export EESSI_USE_ARCHDETECT="${EESSI_USE_ARCHDETECT:=1}"
export EESSI_USE_ARCHSPEC="${EESSI_USE_ARCHSPEC:=0}"
#+end_example
The default selector is =eessi_archdetect.sh=, a shell script that reads =/proc/cpuinfo= against spec files. archspec is off unless explicitly requested. archspec remains the source of the target *names*.
The names of these CPU targets correspond to the names used by archspec.
Both statements remain true for the versions read on 2026-09-10.
A reader debugging target selection needs the script rather than the library.
#+end_detail #+end_detail

#+ATTR_EB: :id EB-Elsewhere-2 :title Which target did you get
#+begin_exercise
A user reports that a job using an EESSI module is three times slower on
one node type than on another, with the same module name loaded.

1. What is the first variable you read, and on which machine?
2. Two mechanisms could produce this. Name both.
3. What would you have to do to confirm which one, and what would you
 have to avoid concluding from a login-node measurement?

#+begin_solution
1. =$EESSI_SOFTWARE_SUBDIR=, on the slow node, inside the job. Not
 =$EESSI_CPU_FAMILY=, which is only =uname -m= and will be the same on
 both.

2. Either that node's microarchitecture has no native build and archdetect
 fell back to a more generic one, which is the fallback policy working as
 designed; or an override is set in the job's environment, naming a
 target that is not the best available. The second is not validated, so
 nothing warns you.

3. Read the ordered list with =eessi_archdetect.sh -a cpupath= on that node
 and compare the first entry against the directory that exists, then
 check the environment for the override variables. What a login node
 cannot tell you is which target a compute node resolves
 detection reads that node's own =/proc/cpuinfo=. Same lesson as
 Four things that actually happened, one layer up.
#+end_solution
#+end_exercise Reading a stack off the wire, CernVM-FS uses a symlink whose stored target is a variable reference. The client expands the variable reference. EESSI provides =host_injections=. The live repository stores it as $(EESSI_HOST_INJECTIONS:-/opt/eessi)=.
Point it to a writable location.
A site obtains a tree that behaves as if it were inside the repository.
* What a site adds without writing to /cvmfs
Three uses are defined.
A stack built elsewhere cannot know the uses.
*GPU drivers.* The driver belongs to the host kernel and cannot be shipped in a repository.
The script =link_nvidia_host_libraries.sh= populates the injection tree with links to the host's driver libraries.
The documentation states: "Re‑run this script each time the NVIDIA GPU drivers on the host system are updated."
It may expose libraries that are new to the driver version.
*A full CUDA installation.* The CUDA and cuDNN packages in the repository contain only runtime libraries.
Compiling CUDA code requires additional components.
The script =install_cuda_and_libraries.sh= installs those components into the injection tree via EasyBuild.
*Site software and site MPI.* The initialisation script derives the site tree from the stack path using string substitution.
#+begin_example
sudo bash -c "echo 'EESSI_HOST_INJECTIONS=/shared_fs/path/to/host/injections/' \
 > /etc/cvmfs/domain.d/eessi.io.local"
sudo cvmfs_config reload
#+end_example
The path =/cvmfs/software.eessi.io/versions/2023.06/software/linux/x86_64/amd/zen2= has a site twin at =/cvmfs/software.eessi.io/host_injections/2023.06/software/linux/x86_64/amd/zen2=.

The path appears on =MODULEPATH= together with the mounted one.

The path corresponds to the three lists described in [[file:10-build-your-own-without-asking.org][Build your own, without asking anyone]].

The site list resides behind a symlink managed by the site.

Per-node-type differences are supported.

The mechanism uses a client-side variable instead of a repository path.

Two GPU node types with drivers in separate locations receive
distinct =EESSI_NVIDIA_OVERRIDE_DEFAULT= values in 2025.06.
=EESSI_HOST_INJECTIONS= still aims the site software tree, not
the NVIDIA compat symlink.
#+begin_example
site_software_path="${EESSI_SOFTWARE_PATH/versions/host_injections}"
export EESSI_SITE_MODULEPATH="${site_software_path}/modules/all"
#+end_example

* What it is, and what it is not

#+ATTR_EB: :id eessi-versions :title Versions and targets, as published :kind reference
#+begin_detail
From [[https://www.eessi.io/docs/repositories/versions/][EESSI versions]]
and [[https://www.eessi.io/docs/software_layer/cpu_targets/][CPU targets]],
read 2026-09-10:

| Version | Toolchains |
|---+---|
| 2023.06 (default) | =foss/2022b=, =foss/2023a=, =foss/2023b= |
| 2025.06 | =foss/2024a=, =foss/2025a=, =foss/2025b= |
| 2026.06 | =foss/2026.1= (catalog still thin; default module hides it) |

The live repository agrees, and says more than the table does. Its root
catalog has exactly three nested catalogs, =/versions/2023.06=,
=/versions/2025.06= and =/versions/2026.06=. Counting modulefiles in every
one of the 165 =modules= catalogs under =/versions/2025.06=, on
2026-09-10: *1079 modules across 529 packages* on each x86_64 target, and
1071 across 526 on each aarch64 target. The same count against 2023.06
gives 1226 modules across 670 packages, and against 2026.06 gives 137
across 132. The live easystack
=eessi-2026.06-eb-5.4.0-2026.1.yml= already lists =foss-2026.1.eb=;
the catalog is what a thin first generation looks like from the
outside. The root catalog's =/init/modules/EESSI/.modulerc.lua= is
consistent with it: it makes 2023.06 the default and *hides* 2026.06.

The 165 is itself the shape of the stack: five aarch64 targets, four of
them with five NVIDIA accelerator subdirectories each, and ten x86_64
targets with thirteen accelerator subdirectories each. Five plus twenty
plus a hundred and thirty.

x86_64 targets: =generic=, =amd/zen2=, =amd/zen3=, =amd/zen4=,
=amd/zen5=, =intel/haswell=, =intel/skylake_avx512=,
=intel/cascadelake=, =intel/icelake=, =intel/sapphirerapids=,
=intel/graniterapids=. aarch64: =generic=, =a64fx=, =neoverse_n1=,
=neoverse_v1=, =nvidia/grace=, =aws/graviton4=. Plus
=riscv64/generic=. Not every target exists in every version; the table
on that page says which, and the fallback list means a host with no exact
match still gets something.

Accelerator targets are named =accel/nvidia/cc<XY>=, and the
initialisation script downgrades a compute capability that has no build
to the nearest lower one ending in zero. In 2025.06 the ones that exist
are =cc70=, =cc80=, =cc90=, =cc100= and =cc120= for NVIDIA, on four
aarch64 targets and all ten x86_64 ones, plus =gfx908=, =gfx90a=,
=gfx942=, =gfx1030=, =gfx1100=, =gfx1101=, =gfx1200= and =gfx1201= for
AMD, x86_64 only. Those counts come from the catalogs rather than from the
GPU-targets page, so they are what is on the wire today.
#+end_detail
Two limits must be stated plainly.
These limits are needed.
The stack is built for a *microarchitecture*.
The fallback allows a host to receive a more generic build than it deserves.
Reading =$EESSI_SOFTWARE_SUBDIR= after initialisation is the check.
The check consists of one line.
The host still provides the driver, the network stack, the filesystem client and the scheduler.
An MPI from the repository communicating with a site fabric matches the case [[file:32-host-injections.org][A site stack next to EESSI, not inside it]].
It is the sole location where "mount it and go" does not cover the entire scenario.
The 2025.06 tree also carries =lfoss/2025b= (the linear-algebra =foss=).
The table above lists the documented common toolchains, not every top-level module.

#+ATTR_EB: :id EB-Elsewhere-1 :title Four machines
#+begin_exercise
For each machine, name the route, the two configuration decisions you
would make, and the one check you would run before believing the result.

1. Your laptop, root available, 40 GB free.
2. A university cluster login node where you have no privileges and the
 administrators are slow.
3. A GitHub Actions runner, for a project whose test suite needs a recent
 compiler.
4. A GPU node whose driver was updated last night.

#+begin_solution
1. Route one, native. Set =CVMFS_CLIENT_PROFILE=single= and raise
 =CVMFS_QUOTA_LIMIT=; 40 GB allows a generous cache and the default
 4000 MB will thrash. Check =$EESSI_SOFTWARE_SUBDIR= after
 initialisation
 fallback list matters.

2. =cvmfsexec=, or a container with =eessi_container.sh=. The decisions
 are where the cache goes, since your home directory may be quota'd and
 on a network filesystem, and which version you pin. Check that the
 modules you need exist for your target rather than in general, with
 =module avail= after initialisation.

3. Either, depending on privileges; the runner is ephemeral so the
 decisions are the cache location and pinning the EESSI version so the
 pipeline does not change under you. Check the first job's wall time
 against the second's: if they are the same, the cache is not being
 reused and every run is paying full price.

4. Route one, plus host injections, and this is the case that needs the
 fourth step. The driver update is exactly when
 =link_nvidia_host_libraries.sh= has to be re-run, per EESSI's own
 documentation. The check is to run something CUDA on that node, not on
 a login node, which is [[file:27-four-things-that-actually-happened.org][Four things that actually happened]]'s whole subject.
#+end_solution
#+end_exercise

#+begin_keypoints
- Three routes onto a machine: a native client with root, =cvmfsexec= or a
 container without it, and the same two on an ephemeral runner where the
 cache is the whole of the install.
- The compatibility layer is why the host distribution stops mattering.
- =eessi_archdetect.sh -a cpupath= returns an ordered list and the first
 target that exists on disk wins, so read =$EESSI_SOFTWARE_SUBDIR= rather
 than assuming.
- Overrides are not validated: a target that does not exist gives an empty
 =module avail=.
- A site adds software and drivers through a variant symlink, without
 writing to =/cvmfs= and without invalidating a signature.
#+end_keypoints
