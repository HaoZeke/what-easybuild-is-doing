Six fields are presented.
They are not equally useful.
The order to read them is not the order they are printed.
*The exit code, first.* 127 is the shell's code for "command not found".
It is not a licence problem nor a permissions problem.
The command being run is absent.
A single number has ruled out most of the search space.
=126= indicates "found but not executable".
=2= usually signals a usage error.
A =make= failure is typically =2=.
The real cause lies further up.
*Then the step.* =in postproc step= indicates that the install already happened.
The problem is not in configure, build or install.
*Then the working directory.* The command ran in =.../wobble-1.0/bin=, which is one level deeper than the archive's top.
Nothing in the easyconfig requested that.
* Why the start directory moved
EasyBuild does not treat the extraction directory as the build directory.
It looks for the real top of the source tree.
The rule is worth knowing [[file:01-an-easyconfig-is-python.org][An easyconfig is Python]]'s failure.

#+begin_detail
=find_base_dir= in =easybuild/tools/filetools.py=, verified against
EasyBuild 5.3.1:

#+begin_example
lst = get_local_dirs_purged()

It descends *while there is exactly one entry*.
It skips dotfiles and a directory named =easybuild=.
The following table shows the mapping.

| The archive contains | The start dir becomes |
|---+---|
| =pkg-1.0/= with several entries | =pkg-1.0= |
| =pkg-1.0/src/= and nothing else | =pkg-1.0/src= |
| =pkg-1.0/bin/wobble= and nothing else | =pkg-1.0/bin= |
| two top-level directories | the extraction directory itself |

An explicit =start_dir= resolves relative to that result.
A =start_dir= suitable for a git checkout may be wrong for a release tarball of the same software.
#+end_detail That rule (see [[dive:start-dir-descent]]) represents the entire failure. =wobble-1.0= contained exactly one entry, =bin=. =bin= also contained a single entry. EasyBuild descended twice. =Tarball= copied the contents of *that* directory into the install prefix. The install tree is: #+end_detail =%(installdir)s/bin/wobble= does not exist.
=%(installdir)s/wobble= exists.
Exit 127 reported the condition.
There are two ways to fix it.
The ways are not equivalent.
=start_dir = ''= stops the descent.
=bin/wobble= is the location the recipe expects.
Alternatively, the =postinstallcmds= line is corrected to the existing path.
The first changes the layout the module exports.
The layout is what a user encounters.
The layout is usually the correct one.

#+ATTR_EB: :id EB-Failure-2 :title Read this log fragment
#+begin_exercise
A log you have never seen, opened at the end and scrolled up:

Identify the step that failed.
Identify the steps that then succeeded.
The build executed =make= for four minutes and terminated with exit code 0.
The termination indicates that the overall build completed without error.
Uncertainty remains regarding the cause of the earlier failure.
The first location to inspect is the log file of the failed step.
The first location will reveal the reason for the failure.
The second location to inspect is the summary of the succeeding steps.
The second location will confirm the successful completion of those steps.
#+begin_example

	make -j 16

#+end_example
1. Determine the failed step.  
1. Determine the successful steps.  

2. The build executed =make= for four minutes and returned exit code 0.  
2. Immediate failures in the =make= process are excluded.  
2. Later runtime errors remain possible.  

3. List the next two locations to examine, in sequence.  
3. Indicate the outcome each location would resolve.
#+begin_solution
1. =sanitycheck= failed, so =configure=, =build= and =install= all
 succeeded: something was compiled and something was installed. The
 twelve steps before the check are not suspects.

2. It rules out a compile failure and a link failure of the thing =make=
 built. It does not tell you that =make install= put anything where the
 easyconfig expected, and it does not tell you that what got built is
 named =libfoo.so=: a library built as =libfoo.so.1.2= with no
 development symlink passes =make= and fails this check.

3. First the install directory, which is still there
 whether the file exists under another name or in another directory.
 Then the =install= step's own commands in the log, which settle whether
 the build system was told a prefix it disagreed with. Nothing in the
 configure output is worth reading until those two are answered.
#+end_solution
#+end_exercise The error block lists the command, the exit code, the cwd, and a path to =out.txt=.
Open that file.
Two logs exist.
Identifying which appears on the page prevents confusion.
A *temporary* log per =eb= invocation is announced as =Temporary log file in case of crash /tmp/eb-*/easybuild-*.log=.
The temporary log is removed when the run succeeds.
A log per installation is named using =easybuild-%(name)s-%(version)s-%(date)s.%(time)s.log=.
On success the log is copied into =<installdir>/easybuild/=.
The log remains with the software.
The line at the end of a failed run is =Results of the build can be found in the log file(s)...=.
The line refers to the second log.
=eb --last-log= prints the path to the most recent log.
It globs the log path.
It retains only files owned by the current uid.
It returns the newest file by modification time.
On a shared build host it finds *your* last log rather than the machine's.
It implies =--terse=.
It enables =vim $(eb --last-log)= to work.
The reading order is often misunderstood.
*Start at the end and work upward.* The last error usually represents fallout.
*Search for the step markers*, not for the word error.
=Starting configure step= and =Running method configure_step part of step configure= split the log into the eighteen sections described in [[file:13-how-a-build-executes.org][How a build executes]].
Knowing the current environment section narrows the search.
*Search for a command, not a complaint.* =running shell command= (or =INFO running cmd= in older logs) lists every command with its working directory and exit code.
Those are the facts.
Searching for =error= yields a compiler's opinion of a header file.

#+ATTR_EB: :id log-search-patterns :title Patterns worth searching a build log for :kind reference
#+begin_detail
From EasyBuild's own troubleshooting guidance, with what each is good
for:

| Pattern | Finds |
|---+---|
| =ERROR= | EasyBuild's own failures, capitalised |
| =Error 1= | a =make= rule that failed |
| =error:= | a compiler diagnostic, with the colon to exclude prose |
| =failure= | test-suite reports |
| =not found= | a missing library or header |
| =No such file or directory= | a path assumption, like this chapter's |
| =Segmentation fault= | a compiler or a test binary crashing |
| =bazel= | Bazel's own log, which is elsewhere |

And the one to avoid: a bare =error=, which matches every occurrence of
the word in every configure script's prose.

The rule that matters more than the list: *look for the first error, not
the last*. Later errors are usually consequences.
#+end_detail

#+ATTR_EB: :id EB-Failure-1 :title Four failures, four first moves
#+begin_exercise
For each, say what you read first and what you would rule out with it.

1. =ERROR: Shell command failed!= with =exit code 2= and
 =in build step=, and the output ends with =make: *** [all] Error 2=.
2. A build that ran for forty minutes and failed in =sanitycheck=, with
 a missing =libfoo.so=.
3. =Couldn't find file thing-2.1.tar.gz anywhere, and downloading it
 didn't work either... Paths attempted (in order):...=
4. A build that succeeds on your machine and fails on a colleague's, same
 easyconfig, same EasyBuild version.

#+begin_solution
1. The =Error 2= is =make= reporting that a rule failed, not the
 failure itself. Read =out.txt= and search upward for the *first*
 =error:=, which is the compiler's. The exit code has told you the
 build system failed rather than EasyBuild, so nothing in the
 easyconfig's structure is suspect yet.

2. The step, and then the install tree. Reaching =sanitycheck= means
 configure, build and install all succeeded, so the software built
 something and it is not what the recipe said it would be. Compare
 =sanity_check_paths= against what is actually in the install
 directory, which is still there. This is
 [[file:06-what-installed-means.org][What "installed" means]]'s check doing its job,
 and the forty minutes are not wasted: the tree is evidence.

3. The list of attempted paths, in order, which is the whole diagnosis.
 It shows every local directory searched, then =source_urls=, then
 EasyBuild's own mirror at =sources.easybuild.io=. If the URL you
 expected is absent from that list, =source_urls= is wrong; if it is
 present and failed, the upstream moved.

4. Neither log alone. This is a difference in environment or
 configuration, so start with =eb --show-config= on both and diff it,
 then compare the loaded modules. What a build is allowed to see's point applies: the
 environments are constructed, and the two of you constructed
 different ones.
#+end_solution
#+end_exercise
