#+TITLE: A toolchain is a hierarchy
#+OPTIONS: toc:nil num:nil

The easyconfig in chapter 1 had one line we did not touch:

#+begin_src easyconfig :widget parse :hydrate load
name = 'code-server'
version = '4.130.0'
toolchain = SYSTEM
#+end_src

=SYSTEM= is the simplest possible value for that line, and almost
nothing on a real cluster uses it. What you will actually see is this:

#+begin_src easyconfig :widget hierarchy
toolchain = {'name': 'foss', 'version': '2025a'}
#+end_src

Read as a name, =foss-2025a= looks like a label for "the 2025a
open-source compiler stack". That reading will cost you an afternoon.
=foss-2025a= is not a name. It is the top of a structure, and that
structure decides which versions of which libraries your package is
allowed to see.

Run the sample. What comes back is not one toolchain, it is a list.

* The list has an order, and the order is the point

The function is =get_toolchain_hierarchy=, in
=easybuild/framework/easyconfig/easyconfig.py=, and its docstring says
what it produces:

#+begin_quote
Determine list of subtoolchains for specified parent toolchain. Result
starts with the most minimal subtoolchains first, ends with specified
toolchain.
#+end_quote

For the =foss= family that list runs =GCCcore=, =GCC=, =gompi=, =gfbf=,
=foss=, each a real toolchain in its own right and each installed as a
real module. Your package declares the last one and gets to depend on
things built with any of them.

That mechanism sits behind a rule you may have absorbed without knowing
why. A =foss= package can depend on a =GCCcore= build; a =GCCcore=
package cannot depend on a =foss= build. Convention and courtesy have
nothing to do with it. A =GCCcore= package's hierarchy does not contain
=foss=, so a =foss= dependency is never a candidate. The robot then
reports that it cannot find something sitting right there on disk.

* The shape is a graph

The =foss= line is a chain, which makes it a bad example for
understanding what the code does. EasyBuild's own docstring picks a
harder one, and draws it:

#+begin_example
        goolfc
        /     \
     gompic    golfc(*)
          \    /   \      (*) optional toolchains, not compulsory
          gcccuda golf(*)
              \   /
               GCC
              /  |
      GCCcore(*) |
              \  |
             (system)
#+end_example

Two toolchains sit at the same level with a shared ancestor, so the
walk cannot be "follow =SUBTOOLCHAIN= upward until it runs out". A
comment in the implementation states it: the search is breadth-first,
"required to take into account the potential for multiple
subtoolchains".

Note the asterisks. =GCCcore= is *optional*. A toolchain class carries
an =OPTIONAL= attribute, and an optional level is included only when it
is actually there. So "the hierarchy of =foss-2025a=" is not a property
of the string =foss-2025a=; it is a property of what is installed.

* The system toolchain is not always in it

Here is the detail that catches people who have read this far and
think they understand it. From the same docstring:

#+begin_quote
The system toolchain is considered the most minimal subtoolchain only
if the =add_system_to_minimal_toolchains= build option is enabled.
#+end_quote

So a =SYSTEM= build is not automatically visible to a =foss= package.
Whether the bottom of the ladder exists at all is a configuration
choice, made by whoever set up the EasyBuild installation. It is off by
default.

If you have ever wondered why a perfectly good =SYSTEM= module refuses
to satisfy a dependency, that is the answer. It is not in your
easyconfig.

* What a toolchain module has to contain

A toolchain occupies a position in a graph. It is also a module, and
the module has to agree with the class. EasyBuild checks:

#+begin_example
List of toolchain dependency modules and toolchain definition do not match
(found [...] vs expected {...})
#+end_example

That comes from =_verify_toolchain= in
=easybuild/tools/toolchain/toolchain.py=, and it fires in the *prepare*
step, seconds in, before anything is unpacked. Three properties of the
check are worth knowing because together they make it unfixable from
your easyconfig:

- It reads the *direct* dependencies of the toolchain module, and only
  those. The call is =dependencies_for(mod_name, ..., depth=0)=. A
  library that arrives transitively does not count.
- It matches on module *name*, so versions and versionsuffixes are
  invisible to it.
- Elements are dropped from the expected set only when they are
  optional and absent, and the base =is_required= returns =True= for
  everything. So a subclass has to opt an element out; nothing opts out
  by accident.

The consequence is a failure mode that looks like your package's fault
and is not. A framework release that renames or splits a toolchain
element breaks *every* package on that generation at once. No
easyconfig parameter reaches the check.

EasyBuild 5.2 did exactly this. In toolchains built on the NVIDIA HPC
SDK (=NVHPC=), the compiler element became a module named
=nvidia-compilers=. Toolchain modules written before the split still
expected the old name.

The tell is that the two lists in the error differ by one element. Read
the lists rather than the package. The difference names the element, and
the fix is a toolchain module that carries it. In practice that means
moving to a generation whose toolchain modules already do.

* The same name can mean two toolchains

One last piece of evidence that a toolchain is not a name.
=get_toolchain_hierarchy= contains this, in full:

#+begin_quote
Stopgap solution until deprecated compiler-only NVHPC toolchain is
removed. Both the new and old NVHPC toolchains share the same name, we
need to selectively filter one out based on the version of the
toolchain.
#+end_quote

Two different toolchain classes, one string. The framework disambiguates
by version number, with a =TODO: delete with EasyBuild 6.0= beside it.

If =foss-2025a= were a label, that code would be unnecessary.

* What to take from this chapter

1. =toolchain= names the *top* of a hierarchy, and the hierarchy is what
   decides which dependencies are candidates.
2. The hierarchy is computed rather than declared. A breadth-first walk
   over a graph produces it. Optional levels appear only when present,
   and =system= sits at the bottom only when the installation puts it
   there.
3. A toolchain module must carry the direct dependencies its class
   expects, matched by name. When it does not, every package on that
   generation fails in the prepare step, and the error is about the
   toolchain rather than about you.

The next chapter is about the number beside a dependency, which looks
like a minimum version and is not one.
