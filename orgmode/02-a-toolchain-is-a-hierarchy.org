The line appears to be a sticker.
It is not.

name = 'code-server'

#+end_src
=SYSTEM= is the simplest value that line accepts.
Real clusters rarely use =SYSTEM=.
Other values appear instead.
#+begin_src easyconfig :widget hierarchy
toolchain = {'name': 'foss', 'version': '2025a'}
#+end_src
=foss-2025a= resembles a label for the 2025a open-source compiler stack.
=foss-2025a= forms the top of a structure.
The structure defines which versions of which libraries a package on this toolchain may see.
[[cite:geimerModernScientificSoftware2014][Geimer, Hoste and McLay 2014]] explains the *module* tree shape.
A Core compiler extends =$MODULEPATH= into a Compiler layer.
An MPI extends the Compiler layer again.
The user types =WRF/3.5= instead of =WRF/3.5-GCC-4.8.2-OpenMPI-1.7.3=.
[[cite:alvarezScientificSoftwareManagement2016][Alvarez, O'Cais, Geimer and Hoste 2016]] add a layer under the compilers, =GCCcore=.
CMake does not rebuild once per toolchain.
Query the sample.
The line does not name a single toolchain.
The line names a list.
* The list has an order, and the order does work
The function =get_toolchain_hierarchy= is defined in =easybuild/framework/easyconfig/easyconfig.py=.
The docstring describes its output.
#+begin_quote
Determine list of subtoolchains for specified parent toolchain. Result
starts with the most minimal subtoolchains first, ends with specified
toolchain.
#+end_quote
Within the =foss= family, the members are =GCCcore=, =GCC=, =gompi=, =gfbf= and =foss=.
Each member is a distinct toolchain and is provided as a module.
The package declares the last one and may depend on artifacts built with any of them.
The ordering is significant and does not follow a simple linear sequence.
=GCCcore= precedes =GCC=, which precedes both =gompi= and =gfbf=, and both precede =foss=.
The two middle entries occupy the same hierarchical level: =gompi= equals =GCC= plus MPI, =gfbf= equals =GCC= plus numerical libraries, and neither is built atop the other.
A displayed list must place one of them first.
The choice carries no semantic weight.
The sample demonstrates this behavior.
A =foss= package may depend on a =GCCcore= build.
A =GCCcore= package may not depend on a =foss= build.
Courtesy does not influence this relationship.
The hierarchy of a =GCCcore= package does not contain =foss=.
A =foss= dependency is never considered.
The system reports the inability to locate the required item on disk.
* The shape is a graph
The =foss= line forms a chain.
The example is poor for understanding the code's behavior.
EasyBuild's own docstring selects a more complex example and illustrates it.
#+begin_example
 goolfc
 / \
 gompic golfc(*)
 \ / \ (*) optional toolchains, not compulsory
 gcccuda golf(*)
 \ /
 GCC
 / |
 GCCcore(*) |
 \ |
 (system)
#+end_example
Two toolchains reside at the same hierarchical level and share a common ancestor.
The walk cannot be described as "follow =SUBTOOLCHAIN= upward until it runs out".
A comment in the implementation notes that the search is breadth‑first.
The search must consider the potential for multiple subtoolchains.
The asterisks indicate that =GCCcore= is *optional*.
A toolchain class includes an =OPTIONAL= attribute.
An optional level is counted only when present.
The hierarchy of =foss-2025a= is not a property of the literal string =foss-2025a=.
It reflects the installed configuration.

#+begin_exercise
Ask the sample above for =foss-2025a= and read the members back.

Now suppose you are writing an easyconfig whose toolchain is
=GCCcore-14.2.0=.

1. Which of the members it printed could your dependencies have been
 built with?
2. Which could they not?
3. A colleague says "but the =foss= module is right there, I can see it
 in =module avail=". What has gone wrong with that reasoning?

#+begin_solution
Your package is on =GCCcore=, so its hierarchy is =system= then
=GCCcore-14.2.0=, and nothing above. A dependency built with =GCC=,
=gompi=, =gfbf= or =foss= is not a candidate.

The direction is the thing people invert. A =foss= package may depend on
a =GCCcore= build. A
=GCCcore= package may not depend on a =foss= build
in the =GCCcore= one.

Your colleague is reading =module avail=, which lists what is installed.
The robot is asking a different question: what is installed *and in this
package's hierarchy*. The module is there. It is not a candidate. The
error says it cannot be found
questions.
#+end_solution
#+end_exercise

* The system toolchain is not always in it
Please provide the org‑mode prose you would like rewritten.
#+begin_quote
The system toolchain is considered the most minimal subtoolchain only
if the =add_system_to_minimal_toolchains= build option is enabled.
#+end_quote
The option changes the walk only when a dependency does not name a toolchain.
=('CUDA', '12.9.1', '', SYSTEM)= still finds the SYSTEM module with or without a flag.
By default the option does not treat a bare =('zlib', '1.3.1')= as also try SYSTEM.
A foss package that omitted the fourth field looks for =zlib/1.3.1-foss-…= or a foss subtoolchain, not =zlib/1.3.1=.
* What a toolchain module has to contain
A toolchain occupies a graph position.
The toolchain also is a module.
The module must conform to the class.
EasyBuild performs checks:
#+begin_example
List of toolchain dependency modules and toolchain definition do not match
(found [...] vs expected {...})
#+end_example
The function =_verify_toolchain= in =easybuild/tools/toolchain/toolchain.py= fires in the *prepare* step, seconds after start, before any unpacking.
Three properties of that check together make it unfixable from an easyconfig.
It reads only the *direct* dependencies of the toolchain module.
The call used is =dependencies_for(mod_name,..., depth=0)=.
A transitively arriving library does not count.
It matches on module *name*; versions and versionsuffixes are invisible to it.
Elements are dropped from the expected set only when they are optional and absent, and the base =is_required= returns =True= for all elements.
A subclass must explicitly opt an element out; no element is omitted accidentally.
The failure appears to be the package's fault, but it is not.
A framework release that renames or splits a toolchain element breaks *every* package in that generation simultaneously.
No easyconfig parameter reaches the check.
EasyBuild 5.2 performed exactly this scenario.
In toolchains built on the NVIDIA HPC SDK (=NVHPC=), the compiler element became the module =nvidia-compilers=.
Toolchain modules written before the split still expect the old name.
The indicator is that the two lists in the error differ by one element.
Read the lists, not the package.
The difference names the element; the fix is a toolchain module that provides it.
In practice this means moving to a generation whose toolchain modules already include it.
* The same name can mean two toolchains

=get_toolchain_hierarchy= contains this, in full:

#+begin_quote
Stopgap solution until deprecated compiler-only NVHPC toolchain is
removed. Both the new and old NVHPC toolchains share the same name, we
need to selectively filter one out based on the version of the
toolchain.
#+end_quote
One string encodes two different toolchain classes.
The system removes the ambiguity using the version number.
